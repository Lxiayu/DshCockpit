# ADR-0006：Live2D 当前阶段不接入生产，仅做渲染接口预留

- **状态**：✅ **已接受（用户 2026-11-01 决策：暂缓生产集成，保留未来 POC 与许可证重新评估可能）** —— 许可证风险最高
- **日期**：2026-11-01
- **决策者**：用户（待确认）
- **影响范围**：Character System、角色素材分发、未来 Character Pack 市场
- **相关文档**：`docs/research/live2d-evaluation.md`（详细评估）、`docs/design/character-system.md`、`docs/adr/ADR-0001`

## 1. 背景

虚拟办公室是 DshCockpit 的核心资产，当前使用 Sprite Sheet（视频拆帧）方案，已有完整的 Character Pack 体系与动画状态机。

用户提出研究 Live2D（Cubism Web SDK），并明确要求：**本阶段只需要制定技术路线和 POC 方案，不要直接将 Live2D 引入生产环境**。

## 2. 事实核查

| # | 事实 | 证据 |
|---|---|---|
| F1 | 当前角色方案是 Sprite Sheet + 视频拆帧，已有可用的 Character Pack 格式（manifest/anchors/animations/expressions） | `src/office/fixtures/character-pack/`、`src/office/runtime/character-pack-installer.js`、`validate-character-pack.js` |
| F2 | Live2D Cubism Core 是**专有二进制**，官方 GitHub repo 的 license 标记为 **NOASSERTION** | `docs/research/live2d-evaluation.md` |
| F3 | Cubism SDK 的 **Expandable Application** 类别**不适用**个人/小微的 Publication License 豁免 | `live2d-evaluation.md` C1–C21 条款表 |
| F4 | 未获 Publication License 而发布 = **违约**，产生损害赔偿 + 禁令风险，并构成解除理由 | 同上（§6.3 违约 / §12 赔偿 / §4.2 禁令） |
| F4b | **销毁义务有前提**：条款原文是「**If this Agreement is terminated pursuant to Section 8.1**, the Customer shall promptly destroy…」——即"解除之后"才触发，不是"发布那一刻自动发生" | `live2d-evaluation.md` §1.6 链路一 |
| F4c | §8.1 的解约是 **Live2D `may`**（裁量），非自动 | 同上 |
| F5 | 官方表述是「**一般规则**」而非绝对排除：紧接一行写「Approval **may** be granted to fully free-of-charge Expandable Applications in some cases if separately specified conditions are met」 | 同上 E2 脚注 |
| F6 | 把 Cubism Core 打进 MIT 安装包**不等于"绝对禁止再分发"**：§5.1/§5.2 是正面再分发授权，§6.2 带「Except as expressly permitted」限定。准确表述是"能分发，但有条件；不能当作 MIT 开源件" | 同上 C 表 |

## 3. 问题

**在当前阶段，Live2D 应该做什么、不应该做什么？**

## 4. 分析

### 4.1 Live2D 能解决什么

| 收益 | 是否真实 |
|---|---|
| 更高的角色表现力（呼吸、视线、口型、物理摆动） | ✅ 真实 |
| 更小的素材体积（参数化 vs 帧序列） | ✅ 真实 |
| 更自然的动态 | ✅ 真实 |
| 降低动画制作成本 | ⚠️ 依赖是否有建模能力（需要 Cubism Modeler 与美术投入） |

### 4.2 Live2D 带来的风险（关键）

| 风险 | 严重度 | 说明 |
|---|---|---|
| **许可证传染** | 🔴 **严重** | Cubism Core 专有；可作为"有条件再分发"部件，但**不能当作 MIT 开源件** |
| **角色素材分发受限** | 🔴 **严重** | 鲸鱼娘作为**可分发角色素材包** → 触发 Expandable Application → **不适用**个人/小微豁免 → 需单独申请（一般规则下免费项目不易获批，但**并非绝对排除**，见 F5） |
| **违约后果** | 🔴 **严重（非自动销毁）** | 未获批发布 = 违约 → 损害赔偿 + 禁令风险 + 构成解约理由；**销毁是解约后的后果，且解约是 Live2D 的裁量**（分层见 `live2d-evaluation.md` §1.6） |
| 技术栈替换成本 | 🟡 中 | 需要重做渲染层与素材管线 |
| 美术投入 | 🟡 中 | 需要建模师 |
| 与现有 Sprite 系统共存 | 🟢 低 | 可做混合渲染 |

### 4.3 核心判断

> **Live2D 的技术收益是真实的，但它的许可证结构与"开源 MIT 项目 + 可分发的角色素材包"这一产品形态根本冲突。**

这不是"以后再说"的问题，而是：**只要我们还打算分发角色素材，采用 Live2D 就必须先解决许可证问题，而这个问题不是我们能单方面解决的。**

### 4.4 与现有方案的对比

| 方案 | 表现力 | 素材体积 | 许可证风险 | 美术成本 | 结论 |
|---|---|---|---|---|---|
| **当前 Sprite Sheet（视频拆帧）** | 中 | 大 | 无（自有素材） | 低（已有管线） | ✅ **保留为生产方案** |
| Live2D | 高 | 小 | 🔴 高（阻断性） | 高（需建模） | ❌ 不进生产 |
| Spine | 高 | 小 | 🟡 中（需 Runtime License） | 高 | 未评估，可作备选 |
| 程序化动画（代码化） | 低-中 | 极小 | 无 | 低 | ✅ 已在用（家具/场景） |
| **Sprite + Live2D 混合** | 高 | 中 | 🔴 高 | 高 | ⏸ 等许可证解决 |

## 5. 备选方案

| 方案 | 描述 | 判定 |
|---|---|---|
| **A. 当前不接，只留接口** | 生产继续 Sprite；Character Controller 抽象出渲染后端接口，为 Live2D 预留位置；做独立 POC 但不分发 | ✅ **采用** |
| **B. 全面替换为 Live2D** | 现在就迁移 | ❌ 否决（许可证风险不可控） |
| **C. 先申请 Publication License 再决定** | 走官方授权流程 | ⏸ **推迟**（成本高、周期长、结果不确定，先不值得投入） |
| **D. 完全放弃 Live2D** | 不再评估 | ❌ 否决（技术收益真实，不该永久关闭） |

## 6. 决策

**采用方案 A。**

### 6.1 做什么（零成本、无风险）

1. **抽象 Character Controller 的渲染后端接口**：
   - 现有 Sprite 渲染是一个实现。
   - 预留 `RenderBackend` 接口，Live2D 可作为第二个实现。
   - **只做接口，不实现 Live2D**。
2. **技术路线文档化**：把 POC 方案写清（`docs/research/live2d-evaluation.md`），让未来接手的人知道怎么做。
3. **许可证路径记录**：把申请 Publication License 的路径与成本写清，作为未来决策依据。

### 6.2 不做什么（明确禁止）

- ❌ **不**把 Cubism Core 打进任何分发包。
- ❌ **不**在 `package.json` 增加 Live2D 相关依赖。
- ❌ **不**开发可分发的 Live2D 角色模型市场。
- ❌ **不**在本阶段做任何 Live2D 实现代码（POC 也只在隔离分支，不进 main）。
- ❌ **不**承诺"未来一定支持 Live2D"。

### 6.3 POC 边界（如果未来要做）

| 项 | 边界 |
|---|---|
| 位置 | 独立分支 / 独立目录，不进生产依赖 |
| 目的 | 验证技术可行性（性能、Pixi 集成、状态机对接） |
| 素材 | 只用 Live2D 官方示例模型（其许可证允许测试） |
| 分发 | **绝不**分发任何含 Cubism Core 的产物 |
| 退出条件 | 明确回答"性能是否可接受""集成成本多少""许可证路径是什么" |

## 7. 决策理由

1. **许可证风险是结构性的，但表述必须精确**：F3–F5 表明这不是"注意一下"的风险——
   Expandable Application 会让我们进入需要单独审批的类别，而审批结果不由我们控制。
   **注意**：这不等于"一发即毁"。准确的责任链是「违约 → 赔偿/禁令 → 可能被解约 → 解约后才销毁」。
   但即便只是"可能被解约"，对开源项目的**可持续性**也是不可接受的依赖。
2. **技术收益不构成现在做的理由**：当前 Sprite 方案已工作良好；表现力提升是"nice to have"，不是用户痛点。
3. **接口预留成本接近零**：抽象一个渲染后端接口是好架构（无论是否用 Live2D），几乎无额外成本。
4. **保留未来可能性**：不永久关闭，但把决策权交给"许可证问题是否解决"这个客观条件。

## 8. 代价

| 代价 | 说明 |
|---|---|
| 表现力上限受限 | Sprite 方案在高动态表现上不如 Live2D |
| 素材体积较大 | 帧序列占空间 |
| 未来迁移成本 | 若将来接入，仍需重做素材管线 |

## 9. 风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| **有人（贡献者）误引入 Live2D** | 中 | 🔴 高 | 在 AGENTS.md 与 PR 模板写明；加 `package.json` 依赖白名单检查（待建） |
| **素材授权链不清**（现有鲸鱼娘素材来源） | 中 | 高 | 已有 `docs/quality/2026-09-26-asset-provenance.md`；需核查覆盖度 |
| 竞争对手用 Live2D 做出更好效果 | 中 | 中 | 我们用"空间化团队交互"差异化，而非单纯卖萌 |
| 用户强烈要求 Live2D | 低 | 中 | 明确告知许可证风险，让用户知情 |

## 10. 后续重新评估的触发条件

满足**全部**条件时才重新考虑：

1. 鲸鱼娘角色素材的**分发模式**已明确（是否作为可分发包）。
2. 已完成 Cubism SDK Publication License 的申请路径评估（成本/周期/成功率）。
3. 有真实用户需求证据表明"Sprite 表现力不足"是使用障碍。
4. 或者：找到**无许可证风险**的等价方案（如 Spine 的授权模式、或纯程序化骨骼动画）。
