# 用户旅程与交互设计

> 状态：**草案（2026-11-01，待用户拍板）**
> 依据：`docs/product/product-vision.md` §4、`docs/architecture/domain-model.md`
> 纪律：**每条交互必须回答"它解决什么真实问题"**。无法回答的交互不进入设计。

## 0. 设计判据

任何界面元素/交互，必须能通过以下三问：

1. **它替代了用户的什么动作？**（如果只是"看起来丰富"，砍掉）
2. **它背后的数据从哪来？**（必须有真实来源，不能编造）
3. **用户不用它会不会更麻烦？**（如果用不到，说明需求不存在）

## 1. 新手初始化（First Run）

### 1.1 真实问题
新手最大的障碍不是"不会点按钮"，而是**不知道要做什么、不知道该装什么**。现有产品（含官方）通常直接给一个空输入框，把全部决策成本丢给用户。

### 1.2 设计原则
**默认零配置可用**。用户第一屏不看到"选择一个 Provider"、"配置 MCP"、"设置工作区"，只看到"你想做什么"。

### 1.3 旅程

```
启动
  │
  ├─ 初次运行 → 欢迎屏（不要求登录、不要求 Key）
  │     │
  │     ├─ 检测依赖：runtime 是否就绪 / 是否已有 key
  │     │     ├─ 缺失 → 就地修复（引导式，可跳过）
  │     │     └─ 就绪 → 直接进入
  │     │
  │     └─ "你想做什么？"（4 张 Starter Kit 卡 + "先随便看看"）
  │           ├─ 选 Kit → 自动装所需 Capability（带进度与可取消）
  │           └─ 随便看看 → 进入示例 Mission（只读演示，可删除）
  │
  └─ 非初次 → 直接进 Mission 列表 / 上次的 Mission
```

### 1.4 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 是否要求配置 API Key 才能进入 | **否** | 先让用户看到价值，再要 Key（Key 只在首次真正执行任务时要求） |
| 是否展示全部能力 | **否** | 只展示 4 个 Starter Kit；高级能力收在"更多"里 |
| 首次是否自动创建 Mission | **是** | 空状态是最差体验；给一个可删除的示例 |

### 1.5 反模式（明确不做）
- ❌ 首次启动弹出 5 步向导（每个步骤都是流失点）。
- ❌ 首次启动要求选 provider/model（用户不知道区别）。
- ❌ 首次启动展示插件市场（信息过载）。

## 2. Starter Kit 选择

### 2.1 真实问题
用户不知道"Agent 能帮我做什么"。抽象的能力列表（"文件操作"、"网页搜索"）对用户无意义。

### 2.2 设计

每张卡回答三个问题：**这是什么 / 我能得到什么 / 需要多久**。

```
┌─────────────────────────┐
│ 📄 帮我写份调研报告       │
│                         │
│ 你说个题目，团队查资料、  │
│ 整理、写成一份 Markdown。 │
│                         │
│ 约 5 分钟 · 产出 .md 文件 │
└─────────────────────────┘
```

### 2.3 关键约束
- 卡片**必须**显示"产出什么文件、大概多久"——这是"5 分钟硬指标"的承诺。
- 卡片**不允许**显示技术术语（MCP / RAG / Provider）。
- 若某 Kit 的平台/依赖不满足 → 卡片置灰 + 一句话原因 + 替代建议。

## 3. Mission 创建

### 3.1 真实问题
用户要的是"做一件事"，不是"建一个项目实体"。传统的"新建项目 → 填表单"是**管理负担**。

### 3.2 设计原则
**Mission 是副产品，不是前置步骤**。用户说一句话，系统自动创建 Mission。

### 3.3 旅程

```
输入框："帮我把这个仓库的 TypeScript 迁移做一半"
  │
  ├─ 幕后：创建 Mission（title 自动生成，可改）
  │         创建 Workstream（默认 1 条）
  │         选取 Starter Kit（code-change）
  │
  └─ 确认屏（轻量，可跳过）
        ├─ "我理解的目标是：……"（可编辑）
        ├─ "边界：只改 src/，不碰 tests/"（可编辑，来自 Kit 默认）
        └─ [开始]
```

### 3.4 与官方的边界
- Mission 创建后**不**自己调度 Agent。调度走官方 Team / Session。
- Mission 只记录"这件事属于哪个项目、目标是什么、边界是什么"。

## 4. Mission Desk（主交互面）

### 4.1 真实问题
用户打开应用想知道的，按重要性排序：

1. **团队现在在干什么 / 卡在哪？**（当下状态）
2. **需要我做什么决定？**（阻塞项）
3. **这个项目进展到哪了？**（宏观）
4. **上次我停在哪？**（连续性）
5. **产出了什么？**（成果）

绝大多数 Agent 产品只回答了 1（甚至只回答"正在运行"）。

### 4.2 信息架构（按问题排序，不按功能排序）

```
┌───────────────────────────────────────────────────────────────┐
│  Mission: TS 迁移                        [状态徽标] [切换 Mission]│
├───────────────────────────────────────────────────────────────┤
│                                                                │
│  ① 需要你（最高优先级，有才显示）                                │
│     ⚠ 团队在等你决定：是否删除 legacy/ 目录                     │
│        [同意] [不同意] [看看详情]                                │
│                                                                │
│  ② 现在在做什么（实时，来自 Harness）                            │
│     researcher 正在搜索  ·  coder 在改 src/api.ts               │
│     （或："团队空闲中，上次活动 2 小时前"）                       │
│                                                                │
│  ③ 项目进展                                                     │
│     Workstream: TS 迁移        ██████░░░░ 60%                  │
│     Workstream: 文档更新        ██░░░░░░░░ 20%                  │
│     已定决策 7 · 待答问题 2 · 产物 4                            │
│                                                                │
│  ④ 上次你停在这里                                                │
│     "决定先迁 api 层，下周一继续" — 3 天前                       │
│                                                                │
│  ⑤ 产物                                                        │
│     📄 migration-plan.md        ✅ 已验证                       │
│     📊 api-layer.diff           ✅ 已验证                       │
└───────────────────────────────────────────────────────────────┘
```

### 4.3 每块的"为什么"

| 区块 | 解决什么 | 数据来源 | 无数据时 |
|---|---|---|---|
| ① 需要你 | 用户最大的焦虑是"它卡住了我不知道" | Harness pending approval/question | 隐藏整块（不显示"暂无"） |
| ② 现在在做什么 | 替代"看日志" | Harness team roster + session 事件 | 显示"空闲 + 上次活动时间"（真实） |
| ③ 项目进展 | 替代"翻历史找进度" | Mission workstreams + 计数 | 显示"刚开始"（真实） |
| ④ 上次停在这 | **这是跨会话连续性的核心体验** | Mission `lastSessionSummary` | 首次则隐藏 |
| ⑤ 产物 | 用户真正要的东西 | Mission deliverable 索引 + 文件校验 | 显示"还没有产物" |

### 4.4 明确不做
- ❌ **不做聊天窗口**（官方已有；违反 ADR-0001）。
- ❌ **不做完整任务列表**（官方 Team 任务板已有；我们在"进展"里只显示计数，详情跳官方）。
- ❌ **不做成员详情面板**（现有办公室悬停卡已覆盖；重复建设）。

### 4.5 交互细节

| 交互 | 行为 | 理由 |
|---|---|---|
| 点"需要你"的卡片 | 就地展开决策所需信息 + 批准/拒绝 | 不给用户跳转成本 |
| 点 Workstream | 展开该工作流的 session 历史与产物 | 从宏观到细节 |
| 点产物 | 系统默认应用打开 / 在文件夹显示 | 不做内置编辑器（重复造） |
| 点"现在在做什么"的成员 | 切到办公室并聚焦该员工 | 空间化理解 |
| 断线 | 顶部细条"连接中断，正在重连"，数据标灰但不消失 | 不制造"数据消失"的恐慌 |

## 5. Shared Context 交互

### 5.1 真实问题
用户需要知道"这个项目已经定了什么、还有什么没定"，但不想读文档、不想翻聊天记录。

### 5.2 设计原则
**共识是活的，不是文档**。每条决策可追溯、可推翻、可过期。

### 5.3 交互

```
Shared Context
├─ 已定决策 (7)                                    [+ 记录决策]
│   ├─ 采用官方 Agent Teams 而不是自研 v1  ✅ 用户确认
│   │    理由：官方已提供 roster/任务板      [证据] [推翻]
│   └─ ...
├─ 待答问题 (2)                                    [+ 提问]
│   ├─ 是否接受 runtime 升级的破坏性变更？  🔴 阻塞 WS-1
│   └─ ...
├─ 已知假设 (3)
│   └─ LayerFS 在 Windows 需要 WSL2  ⏳ 未验证（30 天后过期）
└─ 产出物索引 (4)
```

### 5.4 关键规则

| 规则 | 理由 |
|---|---|
| 决策显示 `decidedBy`（user / agent-confirmed） | 用户要知道哪些是自己拍的板 |
| **Agent 不能直接把东西标为"已定决策"** | 防止模型幻觉污染项目记忆 — 只能"提议"，用户确认 |
| 假设有**过期时间** | 未验证的假设不清理会变成事实错误 |
| 推翻决策时保留原记录 | 追溯"为什么改主意"是长期项目最重要的信息 |
| 每条都有 `[证据]` | 结论必须可追溯（Harness Engineering 原则） |

## 6. Human Inbox（需要你）

### 6.1 真实问题
用户的 attention 是稀缺资源。团队可能同时有多个请求，用户需要**知道哪个最重要、能一次处理完**。

### 6.2 设计

```
需要你 (3)
├─ 🔴 危险  coder 想执行 rm -rf legacy/          [查看命令] [拒绝]
├─ 🟡 决策  researcher 问你选哪个数据源          [A] [B] [都要]
└─ 🟢 确认  reviewer 认为可以合并，确认吗？      [确认]
```

### 6.3 规则
- **按危险度排序**，不按时间。
- 危险操作**必须**显示真实命令原文（可通过展开）。
- **没有"总是允许"**（沿用现有 `office` 审批设计：高危不允许批量放行）。
- 处理后**立即从列表消失**（真实状态，不是动画）。
- 空态**不显示**"暂无待办"占位块（减少噪音）。

## 7. Workstream 管理

### 7.1 真实问题
长期项目通常有 2–5 条并行方向。用户需要知道"每条线卡在哪"，而不是"一共 47 个任务"。

### 7.2 设计

| 层级 | 用户看到 | 粒度 |
|---|---|---|
| Mission | 项目 | 1 个 |
| **Workstream** | **一条工作方向** | **2–5 个** |
| Task Reference | 这次让团队做的事 | 多个（不直接展示为主） |
| Harness Task | 官方任务板里的任务 | 不展示（跳官方） |

### 7.3 交互
- 新建 Workstream：一句话描述方向（不是任务）。
- 拖动排序：调整优先级。
- 标记 blocked：写清"被什么阻塞"（关联 OpenQuestion）。
- **不提供**"批量分配任务"（那是官方 Team 的事）。

## 8. 办公室交互物件

### 8.1 核心原则
> **每个物件必须：① 有真实数据源；② 有点击后的可执行操作；③ 删除它用户会感到不便。**
> 三者缺一，就不做。

### 8.2 物件清单（按优先级）

| # | 物件 | 真实数据源 | 点击后 | 删除它的损失 | 优先级 |
|---|---|---|---|---|---|
| 1 | **项目白板** | Mission 状态（workstream / 决策数 / 未答问题） | 打开 Mission Desk | 失去空间化的项目概览 | **P2 必做** |
| 2 | **收件箱** | Harness pending approval/question | 就地处理 | 需要切窗口才能处理审批 | **P2 必做** |
| 3 | 员工工位 | team roster + session 事件 | 聚焦该成员 + 悬停卡（已有） | — | ✅ 已实现 |
| 4 | 成果展示区 | Mission deliverables | 打开产物文件 | 需要去 Mission Desk 找 | P2 可选 |
| 5 | 会议桌 | 当前 Mission 的 Team 讨论 | 召集团队总结 | 无（可替代） | P3 |
| 6 | 资料架 | Shared Context（决策/发现） | 浏览共识 | 无（Mission Desk 已有） | P3，可能砍 |

### 8.3 已有能力的保护
**已有的悬停卡、员工状态行、时间线、待你处理列表**（`docs/architecture/2026-09-23-office-right-panel-spec.md`）
**已经部分实现了 Human Inbox 与成员详情**。P2 **不重复建设**，而是：
- 把已有的"待你处理"从右栏提升为**空间化的收件箱物件**。
- 把已有的"员工详情"保留在悬停卡里，不新做面板。

### 8.4 文件拖放
**场景**：用户把一个设计稿 / 一份数据拖进办公室。
**做什么**：投递到当前 Mission 的 workspace，成为 Mission 的附件（记录下来源与用途）。
**不做什么**：不做"拖到角色身上让角色吃文件"的装饰性交互。

### 8.5 快捷操作
| 快捷键 | 行为 | 数据 |
|---|---|---|
| `Ctrl+K` | 全局搜索（Mission / 产物 / 会话） | 复用现有 search |
| `Ctrl+Shift+Space` | Quick Ask | 已实现 |
| `Ctrl+Shift+O` | 切到办公室 | 已实现 |

## 9. Companion Mode（伴生模式）

### 9.1 真实问题
用户不想一直开着一个占满屏幕的办公室窗口，但希望**随时知道团队是否需要自己**。

### 9.2 三档形态

| 形态 | 展示 | 何时用 |
|---|---|---|
| **Full Office** | 完整办公室 + Mission Desk | 主动工作时 |
| **Companion** | 鲸鱼娘常驻桌面（小窗，可拖动）+ 状态气泡 | 做别的事时 |
| **Quick Panel** | 托盘/快捷键唤出的小面板（需要你 + 快捷操作） | 快速查看 |

### 9.3 关键约束
- Companion 状态**必须**来自真实事件（有 pending 才提示）。
- **不允许**用随机动画"显得有活力"。
- 资源占用必须可测（Companion 模式 CPU 应显著低于 Full Office）。

### 9.4 与现有代码的关系
- `src/office-rail.js` / `office-rail.html` 已是"窄条 Rail"形态，可作为 Quick Panel 的基础。
- 需要新增的是"真正独立的常驻小窗"（无边框、置顶、可拖动）。

## 10. 成果交付

### 10.1 真实问题
用户做完一件事，需要**拿到东西**并**知道它可信**。

### 10.2 设计

```
Mission 完成
  │
  ├─ 产物清单（每个带：路径、大小、验证状态、产生者、产生时间）
  │     [打开] [在文件夹显示] [复制路径]
  │
  ├─ 验证证据（命令 + 退出码 + 摘要）
  │     ✅ npm test  exit 0  1934 passed
  │
  └─ 下一步建议（基于未答问题）
```

### 10.3 规则
- **没有验证证据不许标"完成"**（已有机械门，`src/work/work-controller.js`）。
- 产物必须落在**用户真实工作区**，不是应用私有目录。
- 所有产物可被下一次任务当上下文引用（`.dsh/` 索引）。

## 11. 交互反模式总表（明确拒绝）

| 反模式 | 为什么拒绝 |
|---|---|
| 右栏做成聊天窗口 | 与官方正面对撞（ADR-0001） |
| 所有 Agent 都在动 = "看起来很忙" | 违反"不伪造"；动画不是执行证据 |
| "总是允许"按钮 | 安全风险（沿用现有高危审批设计） |
| 空状态填满占位内容 | 噪音；用户分不清"真的没有"和"还没加载" |
| 首次启动强制 5 步向导 | 每个步骤都是流失点 |
| 装饰性交互物件（如摸头杀） | 违反"每个物件必须有真实数据 + 操作" |
| 在办公室内嵌完整聊天 | 空间隐喻被破坏，且与官方重复 |
| 自动把 Agent 的话当"决策" | 污染项目记忆 |
