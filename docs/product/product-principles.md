# 产品与工程原则

> 状态：**现行（2026-11-01）** · 本文件把用户要求的「第一性原理」与「OpenAI Harness Engineering」转化为 DshCockpit 可执行的判断规则。
> 用法：任何设计、PR、Issue、ADR 都必须能通过 §2 的「八问」与 §4 的「强制化清单」检查。
> 这不是建议清单，是**评审依据**。违反需要写明理由并由用户拍板。

## 1. 第一性原理工作法

### 1.1 强制八问（任何新功能/新依赖前必须书面回答）

1. **用户真正要解决的问题是什么？**（不是"想要什么功能"，是"现在的痛点"）
2. **问题产生的根本原因是什么？**（缺工具？缺信息？缺流程？还是历史设计遗留？）
3. **哪些是客观技术约束，哪些只是历史遗留？**
4. **当前方案是否只因为"过去这样实现"而继续？**
5. **是否存在更简单、更稳定、更容易维护的方案？**
6. **哪些能力已由 DeepSeek Harness 或第三方提供？**（必须先查官方 308 个包）
7. **我们真正需要自己拥有的核心能力是什么？**
8. **为什么必须开发这一功能，而不是接入已有能力？**

**第 6 问的强制动作**：在提出任何"自研 X"之前，必须先执行：

```bash
# 官方能力盘点（本机 0.2.1-rc.5 asar 内实测 308 个 @deepseek-ai 包）
node /tmp/asar_inspect/extract.js /dsh/package.json        # 依赖清单
ls ~/.dsh/profiles/node_modules/@deepseek-ai | grep -i <关键词>
```

并在 Issue/ADR 中写出检索结果。**"我查过，官方没有" 必须附证据；不查就是违规。**

### 1.2 已确立的反模式（本项目的具体教训）

| 反模式 | 为什么错 | 本项目实例 |
|---|---|---|
| 看到一个有趣的开源项目就集成 | 集成成本远大于收益，且往往与官方重复 | 评估 Obelisk/OpenViking 前必须先证明 `dsh-goal` + `dsh-compaction` + session-search 不够 |
| 概念先进就必须支持 | Live2D/Mission/Capability Platform 都是"有道理"，不等于"现在要做" | Live2D 只做 POC，不进生产 |
| 为了扩展性先造抽象 | 只有一个实现时的抽象是负债 | Harness Adapter 抽象推迟到出现第二个 Adapter |
| 把"看起来像"当成"是" | 动画不是执行证据 | 办公室活动状态 ≠ Agent 真实运行状态 |
| 用 Markdown 文件解决记忆问题 | 无索引、无版本、无审核的文档等于不存在 | Shared Context 必须是结构化 + 可追溯 |
| 用聊天窗口当主界面 | 与官方正面对撞 | 右栏不做第二个聊天窗口 |

## 2. Harness Engineering 的本地化落地

来源：OpenAI《Harness engineering: leveraging Codex in an agent-first world》（2026-02）。以下每条都落到**本仓库的具体机制**，不是口号。

### 2.1 重新定义工程师的角色 → 人掌舵，Agent 执行

| 原则 | 本地化落地 | 落地位置 |
|---|---|---|
| 人负责目标、边界、验收、抽样 | 用户拍板 plan 后才动工 | `AGENTS.md` §4.1 |
| Agent 负责执行、自检、迭代 | 执行证据必须来自真实命令退出码 | `src/work/work-controller.js`（无产物不算完成） |
| 不做微观管理 | 规则用门禁强制，不写进 prompt 长文 | `test/*.test.js` 的边界门禁 |

### 2.2 提高应用程序的可读性 → Agent 必须能真正跑起来

**判据**：一个 Agent 拿到仓库，不读聊天记录，应能在 **10 分钟内**：
`npm install` → `npm test` → 知道哪条红 → 定位到文件 → 跑起来看到界面。

当前缺口（待补，见 `docs/quality/testing-strategy.md`）：
- 真机 Electron 探针不稳定（`test/office-ui.test.js:1294` E5a-R1，基线唯一红）。
- 缺少"启动应用并截图"的标准工具。
- 缺少结构化的运行日志读取入口（现在要人肉 `~/.dsh/`）。

### 2.3 仓库是记录系统 → 禁止信息只存在于聊天里

**硬规则**：以下信息**一旦产生，必须在同一批次内落盘**，否则视为工作未完成：

| 信息类型 | 必须落到 |
|---|---|
| 产品需求/定位 | `docs/product/` |
| 架构决策（有取舍） | `docs/adr/ADR-NNNN-*.md` |
| 技术方案 | `docs/architecture/` |
| 开发计划 | `docs/plans/active/` |
| 完成报告 | `docs/plans/completed/` |
| 研究结论（带证据） | `docs/research/` |
| 已知问题/待办 | GitHub Issue |
| 质量规范 | `docs/quality/` |

**反例**：本文件所属的这一轮工作，如果只留在对话里而没有写进 `docs/`，就是违规。

### 2.4 目标是智能体的可读性 → 文档结构服务于检索

- `docs/README.md` 是**唯一索引**，由 `test/docs-index.test.js` 机械校验（未登记 = 测试红）。
- `AGENTS.md` 是**地图不是手册**，硬上限 130 行（同样有测试）。
- 每份文档开头必须有：**状态**（现行/草案/已废弃）+ **日期** + **上游依据**。
- 结论必须可追溯到证据：文件路径 + 行号，或命令 + 输出。

### 2.5 规范架构与品味 → 用工具强制，不靠自觉

见 §4「强制化清单」。核心思想：**能变成测试的规则，就不要只写在文档里。**

### 2.6 吞吐量改变合并理念 → 小步、可回退、每步有证据

| 规则 | 落地 |
|---|---|
| 小步提交 | 一个 commit = 一个自洽可回退的变更 |
| 每批独立可回退 | 回退单文件用 `git restore --source=HEAD -- <file>`（允许） |
| 提交信息写"为什么 + 证据" | 测试数/变异结果写进 commit body |
| 禁止破坏性 git | `reset --hard` / `clean -fd` / `checkout -- .` / `add -A` 全禁 |

### 2.7 不断提高的自主水平 → 分级授权

| 级别 | 场景 | 要求 |
|---|---|---|
| L0 | 只读审计、文档整理 | 无需确认 |
| L1 | 单文件修复 + 有测试覆盖 | 计划写在 commit message |
| L2 | 跨模块改动 | 先写 `docs/plans/active/` 计划并等用户拍板 |
| L3 | 改 Runtime 生命周期 / 数据库迁移 / 公开接口 | 计划 + ADR + 用户明确批准 |

### 2.8 熵与垃圾收集 → 持续质量治理

**每批次收尾必须执行**（对应 `docs/quality/tech-debt-inventory.md`）：

1. 有没有新产生的技术债？（记入 tech-debt-tracker）
2. 有没有文档与代码矛盾？（矛盾文档优先修正或归档，不允许留在活跃区）
3. 有没有未被测试覆盖的核心逻辑？
4. 有没有不再被使用的模块/文件？
5. 有没有重复实现（尤其是与官方重复）？

**周期性**（每次里程碑）：
- 全仓扫描"与官方能力重复"的模块 → 决定保留/让位/删除。
- 核对 `docs/README.md` 索引与实际文件一致（已有测试）。

## 3. 架构判断规则（比"原则"更具体）

### 3.1 事实作者唯一性

任何状态**只能有一个写入者**。设计时先回答："这个状态谁写？"
如果答案是"两边都写"，方案就是错的。

### 3.2 派生优于存储

能从真实事件算出来的，不要存。
- ✅ Office 活动状态 = fold(真实事件)
- ❌ Office 活动状态 = 独立定时器 + 自己的数据库

### 3.3 不伪造

没有证据就没有"完成"。三类具体禁止：
- 执行层不得生成 prompt 内容。
- UI 不得在无数据时填充"看起来合理"的默认值。
- 报告不得把未通过的测试写成通过。

### 3.4 隐私边界不因新功能放松

进入事实链与 Office 快照的**只允许**：派生句柄（`exec-*` / `team-*-sha256:*`）、闭集 token、计数、金额。
**永不进入**：raw sessionId、prompt 正文、工具参数原文、产物内容、绝对路径。

### 3.5 新手默认安全

任何第三方 Provider / 插件 / 工作区隔离能力：
- **默认不安装**（opt-in，不是 opt-out）。
- 安装前必须过"健康检查 → 试用 → 可卸载"三段验证。
- 平台不支持时必须**明确拒绝**，而不是"安装后崩溃"。

## 4. 强制化清单（规则 → 机制）

**这是本文件最重要的部分**：把"应该"变成"不可能违反"。

| 规则 | 已强制？ | 机制 |
|---|---|---|
| `docs/` 每个文件必须被索引 | ✅ | `test/docs-index.test.js` |
| `AGENTS.md` ≤ 130 行 | ✅ | 同上 |
| 索引不得有死链 | ✅ | 同上 |
| `src/team/runtime/**` 零 Electron/DOM/fs/网络 | ✅ | 纯 Node 门禁测试 |
| `src/office/runtime/**` 零 DOM/Pixi | ✅ | 同上 |
| office-module 的 require 集合冻结 | ✅ | 集合相等断言 |
| 执行层不得调用 Team 命令（单一转换点） | ✅ | `test/exec-contract` M14 |
| 渲染层不得成为事实源 | ✅ | 静态 import 断言 |
| Office 快照隐私字段白名单 | ✅ | `privacy-redactor` + 测试 |
| `office:*` 通道集合冻结 | ✅ | 契约测试 |
| 无产物不得显示"完成" | ✅ | `work-controller.js` 状态机 |
| 文档与代码矛盾 | ⚠️ 靠人工 | 待加：文档事实抽查 |
| 与官方能力重复 | ⚠️ 无检测 | 待加：官方包清单对照脚本 |
| 新增依赖的许可证合规 | ⚠️ 无检测 | 待加：license allowlist 检查 |
| 未使用模块 | ⚠️ 无检测 | 待加：dead-code 扫描 |
| Capability Pack 健康检查 | ❌ 未实现 | 设计阶段（见 capability-platform） |
| Mission 数据 schema 校验 | ❌ 未实现 | 设计阶段 |

**行动规则**：新增架构规则时，先问"这条能变成测试吗？"
- 能 → 写测试，不写进文档正文（或文档只写"见测试 X"）。
- 不能 → 写进文档，并在 tech-debt-tracker 记一条"为何无法强制化"。

## 5. 评审 Checklist（每次 PR / 批次收尾）

**功能**
- [ ] 解决的是真问题（八问已答）
- [ ] 没有重复实现官方已有能力
- [ ] 没有引入不必要的抽象
- [ ] 公开接口未随意改变

**正确性**
- [ ] 有测试覆盖，且通过了负向变异（破坏→红→还原→绿）
- [ ] 无法被变异检出的测试已如实标注 masked
- [ ] 边界情况（空数据、断线、损坏、超时）有处理

**边界**
- [ ] 没有第二个事实作者
- [ ] 没有把派生状态当存储
- [ ] 隐私边界未被放松

**可维护性**
- [ ] 文档已同步（索引 + 相关架构文档）
- [ ] 技术债已登记或已消除
- [ ] 变更可独立回退
