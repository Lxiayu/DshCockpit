## 2. 离线测试测不到什么

`office-right-panel-p3.test.js` 覆盖的是**纯逻辑**：risk 分类、
payload 校验、`answerPending` 的接受/拒绝形状。

它不会告诉你：

| 只有真机能验证 | 为什么重要 |
|---|---|
| 卡片真的渲染出来了吗 | 纯函数返回对了 ≠ DOM 呈现对了 |
| 高/低风险的标记**视觉上**不同吗 | 只是数据字段不同，用户看不出区别 |
| 计数为 0 时徽标真的降为中性吗 | 警示红在零待办时制造"有东西待办"的错觉 |
| 就地处理按钮真的**在卡片里**吗 | 只有模态里能处理就不满足"就地"标准 |
| 运行时重启后的失效说明真的显示吗 | 那是"为什么刚才的卡不见了"的唯一解释 |

## 4. 探针设计：两处刻意的选择

### 4.1 截图必须在卡片在场时拍

第一版只在最后拍一张，结果拍到的是**最终态**（运行时重启后的失效说明），
看不到卡片——最有价值的视觉证据丢了。

现在拍两张：卡片在场时一张（`office-inbox-with-cards.png`），
最终态一张。守卫断言"卡片截图必须早于清空收件箱"。

### 4.2 状态推进走 `office:state` 推送，不手动注入

白板验收已经证明：页面订阅 `bridge.onState`，手动 `applySnapshot`
会被后续推送覆盖。所以这里直接改 stub 的 `office:state` 返回值并
用 `webContents.send` 推一次——**走真实链路**。
