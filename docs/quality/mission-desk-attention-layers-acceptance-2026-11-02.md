# 待办两层分类 验收（2026-11-02）

## 0. 为什么必须分两层

GPT 第三轮的原话：

> 「这八种东西不能全部混成一个普通列表……这样用户不至于每次打开办公室
> 都看到一堆红色警告。」

我第一性原理复述一遍：

**如果所有东西都用红框，用户会学会无视红色 —— 第一层就失效了。**

这是"警报疲劳"：当一个界面把所有事情都标红，红就不再意味着"紧急"。

## 1. 分法

| 层 | 内容 | 判断依据 | 视觉 |
|---|---|---|---|
| **第一层：需要你决策** | approval / question / plan-review | **阻塞团队**，不回答就进行不下去 | 红框 + 红竖条 + 可操作按钮 |
| **第二层：执行提醒** | 排队输入 / 权限风险 | **不阻塞**，但用户看不见会误判 | 中性底 + 彩色细线 + 无边框 |

## 2. 第二层的数据源（只有真实来源）

我刻意只接入**两个有真实数据**的提醒：

### 2.1 inbox 排队输入

来自 `session/projections` 的 `inbox`：

```ts
interface InboxProjection {
  nextTurn: UserMessage[];   // 等待后续单独执行
  nextStep: UserMessage[];   // 等待下一个 Agent 步骤
}
```

**为什么值得展示**：用户连续交代几件事后，如果看不到队列，
会误以为 Agent 没收到。这是**执行透明度**，不是任务管理。

**只取计数 + 一句摘要**，不把完整消息搬进右栏（那是第二个聊天框）。

### 2.2 权限风险

来自 `permissions.currentValue === 'danger-full-access'`。

**为什么值得展示**：这是最高权限，工具调用不受工作区沙箱限制。
如果不是用户有意选的，应该知道。

## 3. 刻意**没有**做的（没有数据源，做了就是编造）

| 提醒 | 为什么不做 |
|---|---|
| TeamTask `blockedBy` 阻塞 | 需要先启用 team profile（下一项任务） |
| `writeScopeWarnings` 文件冲突 | 同上 |
| "长时间无进展" | 需要心跳 + 事件 + 任务三者综合判断，本轮不做 |
| Deliverable 待验收 | 审查状态机还没做（缺口 B） |

**「没有数据就不显示」是硬约束。** 零数据时验证过：不编造提醒块。
