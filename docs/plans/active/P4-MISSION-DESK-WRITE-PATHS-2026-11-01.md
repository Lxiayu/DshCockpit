# Mission Desk 写入入口 —— 第一性原理分解

> 状态：执行中（2026-11-01）
> 上游：独立盘点审计（`docs/product/gap-inventory.md` §5.5）
> 触发：审计发现 18 个 action 中 **7 个无 UI 出口**

## 1. 问题：Desk 是个只读报表

Mission Desk 是 P1 的"首个用户可见界面"。但审计核实后发现：
**用户只能看，不能记录。**

| action | 审计结论 | 后果 |
|---|---|---|
| `recordDecision` | 无 UI | Brief 的"决策"段**永远空** |
| `registerDeliverable` | 无 UI | `deliverables` **永远空** |
| `addWorkstream` / `updateWorkstreamStatus` | 无 UI | 工作流只能看 |
| `update` | 无 UI | 标题/目标不可改 |
| `openQuestion` | 无 UI | （`answerQuestion` 有 UI，但没法先提问） |
| `openDesk` | 无 UI | 已由 `office:open-desk` 解决（上一轮） |

**这直接否掉了两条已宣告的价值主张**：
- V2「跨会话不丢决策」—— 没有记录决策的通道
- V3「产物是真实文件」—— 没有登记产物的通道

## 2. 第一性原理：Desk 的本质是什么

先问清楚：Mission Desk 到底该是什么？

**它不是"项目仪表盘"**（那只是展示）。它是**Mission 的编辑器**——
用户在这里把"脑子里想的事"变成"结构化的、跨会话不丢的事实"。

从这个定位推导出三个必须成立的读写对：

| 用户想做的事 | 需要读 | 需要写 |
|---|---|---|
| "我决定了 A 而不是 B" | 决策列表 | `recordDecision` |
| "这个文件是产物" | 产物列表 + 校验状态 | `registerDeliverable` |
| "这条线索在有推进" | 工作流列表 | `addWorkstream` / `updateWorkstreamStatus` |

**没有写入的 Desk 不叫 Desk，叫报表。** 报表不能支撑"跨会话不丢"。

## 3. 第二性原理：为什么这些 action 会没有 UI

不是因为难。三个真实原因：

1. **它们不是创建 Mission 的必经路径**——先做了 create/list/get/status 这条主线
2. **没有验收要求**——真机验收只查渲染，不查"能不能写入"
3. **写入需要表单**，表单比展示贵（要校验、要错误提示、要防重复提交）

第 1、2 条是流程问题，第 3 条是成本问题。所以修法要**同时**处理：
补 UI（解决 1、3）+ 补验收（解决 2）。

## 4. 顺带修一个治理漏洞（审计 B-4）

```js
// src/ipc-mission.js:264-266（现状）
status: payload.status || 'accepted',
decidedBy: payload.decidedBy || 'user',
```

任何调用方（包括未来的模型）不传这两个字段，写出来的就是
"**用户已接受的决策**"。而 `user-journeys.md` §5.4 明确要求：
「Agent 不能直接把东西标为"已定决策"」。

**规则写在文档里，没有写成代码。** 这轮要把它变成代码。

推导：默认值不能是"已接受 + 用户"，应该是
"**待确认 + 来源未知**"——让"已接受"成为一个需要显式声明的动作。

## 5. 实施分解

| 步 | 内容 | 验证 |
|---|---|---|
| **S1** | 修 `recordDecision` 的默认值（治理漏洞） | 单测：不传 status/decidedBy 时不是 accepted/user |
| **S2** | Desk 加「记录决策」表单 | 离线契约测试 + 真机 |
| **S3** | Desk 加「登记产物」表单 + 「打开/定位」 | 同上 |
| **S4** | Desk 加「工作流」新建 + 状态切换 | 同上 |
| **S5** | 真机验收（真实写入 → 确认落盘 → 重启后仍在） | 探针 |

S1 先做：**治理漏洞比功能缺失更严重**——缺功能是"用户用不了"，
错默认值是"用户以为 Agent 的猜测是他自己的决定"。

## 6. 验收标准

- [ ] 不传 status 时，决策状态**不是** `accepted`
- [ ] 不传 decidedBy 时，来源**不是** `user`
- [ ] UI 能记录决策，且记录后 Brief 的决策段出现内容
- [ ] UI 能登记产物，且**真机验证文件确实存在**（不是只写个路径）
- [ ] UI 能建工作流并改状态
- [ ] 写入后**重启 Desk 仍在**（持久化真的生效）
- [ ] 所有写入失败都有可读原因（不只 `{ok:false}`）

## 7. 明确的非目标

- ❌ 不做富文本编辑器
- ❌ 不做决策的"推翻"流程（审计指出 `decision.superseded` 无 action，
  但那是独立功能，先不混进来）
- ❌ 不改 Brief 生成逻辑
