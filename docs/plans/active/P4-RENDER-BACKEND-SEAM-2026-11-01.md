# RenderBackend 接口预留 —— 第一性原理分解

> 状态：执行中（2026-11-01）
> 上游：ADR-0006 §6.1「抽象 Character Controller 的渲染后端接口…**只做接口，不实现**」
> 触发：审计指出这是"已接受 ADR 里唯一零成本无风险的动作，却没做"

## 1. 先质疑这个任务

repo-map.md §2.6 写着：**「只有一个实现时不造接口；出现第二个实现且有替换需求时才抽象」**。

而当前确实只有一个实现（`pixi-office-renderer.js`，4673 行）。
按这条铁律，**不应该造 `RenderBackend` 接口**。

那 ADR-0006 §6.1 为什么要它？先看清这一点，否则做出来就是负债。

### ADR-0006 的理由（原文）

> 1. **抽象 Character Controller 的渲染后端接口**：
>    - 现有 Sprite 渲染是一个实现。
>    - 预留 `RenderBackend` 接口，Live2D 可作为第二个实现。
>    - **只做接口，不实现 Live2D**。

### 两条规则的冲突与裁决

| 规则 | 说什么 |
|---|---|
| repo-map.md §2.6 | 一个实现时不造接口 |
| ADR-0006 §6.1 | 预留接口，Live2D 是预期中的第二实现 |

**裁决：两者其实不冲突，但前提是"接口"的定义要收窄。**

- ❌ 如果做成"完整的 RenderBackend 抽象层"（把 4673 行的每个方法
  都抽成 interface + adapter），那是**负债**：多一层间接、多一份要同步的契约、
  而且没有第二个实现来验证抽象是否正确。
- ✅ 如果只做**"接缝声明"**——记录"哪些地方是渲染后端特有的"，
  并用**一个薄的可替换点**承载——那成本接近零，且未来真接 Live2D 时
  不需要重新考古 4673 行代码哪里是耦合点。

所以我做的不是"抽象层"，是**接缝（seam）**。

## 2. 第一性原理：接缝与抽象层的区别

| | 抽象层 | 接缝 |
|---|---|---|
| 目的 | 让两个实现可互换 | **标出未来会换的地方** |
| 成本 | 每加一个能力都要改 interface | 一次性标注，不改现有代码 |
| 何时做 | 已有第二个实现 | **预期有第二个实现，但现在没有** |
| 风险 | 抽象错了要重构两遍 | 几乎无风险 |

ADR-0006 说"只做接口，不实现"——它要的是**接缝**，不是抽象层。
把它理解成"造完整 interface"是过度实现。

## 3. 接缝应该标在哪

看渲染器对外暴露的 20 个方法，按"是否与具体渲染技术绑定"分类：

| 方法类别 | 例子 | 与 PixiJS 绑定？ |
|---|---|---|
| **生命周期** | `resize` / `destroy` / `pause` / `resume` | ❌ 任何后端都需要 |
| **状态查询** | `diagnostics` / `hitTest` / `officeDiagnostics` | ❌ 语义无关技术 |
| **交互** | `setSelection` / `beginDrag` / `dragTo` / `endDrag` | ❌ 语义无关技术 |
| **显示控制** | `setVisible` / `setReducedMotion` / `setPresenting` | ❌ 语义无关技术 |
| **主题** | `setSceneTheme` | ⚠️ 部分（颜色 token 通用，应用方式不同） |
| **绘制顺序** | `groundPaintOrder` / `furniturePaintOrder` | ✅ **PixiJS 特有**（z-order/容器树概念） |

**关键发现：20 个方法里只有 2 个是渲染技术特有的。**

这意味着：
- 现有接口面**已经基本是后端无关的**——好消息，说明当初设计得不错
- 真正需要预留的接缝很小：只需声明"后端契约 = 这 18 个方法"，
  并把那 2 个标注为"可选/后端特有"

## 4. 实施：一个契约声明，不是抽象层

`src/office/render/render-backend-contract.js`：
- 定义 `BACKEND_CONTRACT`（必需方法清单）+ `BACKEND_OPTIONAL`（后端特有）
- 提供 `assertBackendShape(impl)` —— 检查一个实现是否满足契约
- **不改变** pixi 渲染器的任何代码
- **不引入** 任何适配层

这样：
- 未来接 Live2D 时，照这个清单实现即可
- 现有渲染器可以被这个函数检查（验证契约是否与现实一致）
- 零运行时成本（只在测试里用）

## 5. 验收标准

- [ ] 契约清单与真实渲染器的方法面**一致**（用测试断言）
- [ ] 契约不包含任何 PixiJS 特有概念（除了明确标注的可选项）
- [ ] `assertBackendShape` 能正确识别缺失方法
- [ ] **不引入运行时依赖**：现有代码路径一行不改
- [ ] 文档写清"这是接缝不是抽象层"

## 6. 明确的非目标

- ❌ 不做 adapter 层
- ❌ 不把 pixi 渲染器拆成多文件
- ❌ 不实现 Live2D
- ❌ 不改变任何现有调用方
