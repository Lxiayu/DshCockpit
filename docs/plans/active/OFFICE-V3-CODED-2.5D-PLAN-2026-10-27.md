# OFFICE V3 代码化 2.5D 场景方案（2026-10-27，用户提出）

## 1. 背景与问题

用户原话（2026-10-27）："我所有的家具还有物品以外，都是用图片素材放上去拼接的，
看上去的观感其实没有那么好，并且有的时候，鲸鱼娘在走到附近的时候会穿模，并且
关于这些图片素材的复用和管理也比较麻烦。……我想让你直接生成家具这一类的内容，
以达到比用图片素材拼接更好的展现效果。……不用按照我现在的家具布局来看看你有
什么方案。"

归纳成三条要解决的问题：

1. **观感**：贴图拼贴在缩放/对齐/光照不一致时显得脏、飘、没有统一材质。
2. **穿模**：家具和角色分属固定图层（back-furniture / ground-entities /
   front-occluders），角色永远夹在中间，走到桌后/桌侧时遮挡关系是错的。
3. **资产维护**：每件家具都要一张图 + 一个 assetId + 一个校准条目；复用难、改版贵。

## 2. 方向：类平面 2.5D（不换投影）

- 保持现有平面构图（相机不斜放、不压缩视野），家具用"**顶面 + 前立面**"两块
  梯形/矩形画出厚度，靠明度与接缝线表现材质——即经典 2.5D 游戏的做法。
- 深度排序用**前下边缘的屏幕 y**（与角色脚点同一坐标），家具与角色走**同一次
  画家算法**，从根上消灭穿模，而不是靠调图层。
- 颜色全部来自 `code-scene.js` 的两套主题调色板（浅色/中性灰暗色），不新增贴图。

## 3. 画法规则（可复用的"家具语法"）

每个部件是一个轴对齐盒子，世界坐标 `(x0,y0,x1,y1)` + 高度 `(z0,z1)`：

- **顶面**：footprint 向上抬 `z1` 后画矩形（平涂 + 1px 内描边）。
- **前立面**：从 `y1` 处 `z0→z1` 的矩形（比顶面暗一档）。
- **接缝线**：顶面与立面的交界用 `edge` 色 1px，保证低对比材质也能分开。
- **细节层**：屏幕/键面/抽屉线/把手/水槽/杯口等，画在对应面上方 0.5px。
- **接触阴影**：每个"定义占地"的部件在地面投一块椭圆或矩形，暗色更重。
- **分组**：一个工位拆两组（椅组 / 桌组）。椅组内含靠背、气压杆、五星脚、
  坐垫，整组画在角色之前（即更远），桌组画在角色之后。**没有"坐垫组"**：角色
  是正面朝镜头的立绘，桌子和椅子都在座位之后，任何画在角色前面的坐垫都会变成
  第一版截图里那块"浅灰色柜子"（见 §8）。

## 5. 遮挡契约（防穿模）

- 角色键 = 脚点 `y`；家具组键 = 前下边缘 `y1`。**不做坐姿重挂键**（原方案的
  station band 机制已删除）：角色立绘正面朝镜头，桌/椅都在座位之后，脚点键本身
  就给出正确的前后关系；把坐姿角色重挂到"桌子之前"会把她的上半身切掉（§8 实测）。
- 走动：走到桌后（y 更小）被桌子挡住，走到桌前（y 更大）画在桌子之上——
  连续、无跳变，不再依赖固定图层。遮挡来自几何，而不是层。
- 命中测试仍以脚点为圆心，不随绘制顺序变化；拖拽/聚焦仍是纯呈现，不产生
  office 动作（真壳探针：`officeActions: 0`）。

## 6. 落地步骤

1. `code-office.js` 重写为世界坐标套件（`groups` + `stations` + `stats`），
   保留"座位锚点决定工位"的功能语义；装饰只占用空地。
2. 渲染器新增 `drawOfficeGroup()`，按组创建持久 Graphics，加入
   `ground-entities` 的统一排序（角色 + 家具）。
3. 开关仍是 `?officeLayout=generated`，默认关闭；截图验收后再决定是否默认。
4. 验收：亮/暗截图、走位多帧截图（桌后/桌前各一帧）、全量测试、性能
   （组数 ≈ 6×3 + 4，静态零重绘）。

## 7. 与"图片素材"的关系

- 角色（鲸鱼娘）仍用已验证的 PNG 帧，不动。
- 家具、道具、环境全部由代码绘制后，`resources/office` 的家具贴图与
  `layout-assets.js` 的家具目录可以逐步退役；角色帧引导线清理
  （`frame-hygiene.js`）继续保留。
- 退役顺序：generated 模式验收 → 默认切换 → 删除未使用的贴图与校准条目
  （单独一次清理提交，避免和视觉改动混在一起）。

已修复的三个原型缺陷（留档，避免回退）：

1. **桌子变柜子**：第一版有通宽前挡板（modesty panel 画在了前侧），桌面以下
   整块米色，椅子完全看不见。改为"挡板在后 + 侧板落地 + 抽屉柜落地"。
2. **浅灰柜子盖住角色**：第一版把坐垫放在"角色之前"的第三组，正面立绘的

3. **窗与茶水间打架**：高柜/壁架的 z 抬升让它们在屏幕上爬进窗玻璃。generated
   模式把窗挪到墙面空档，并把光斑改成椭圆。

- 空工位的椅背只露出桌面下的一条（几何上正确，但看起来像小显示器）；考虑

- 沙发仍偏"长凳"，扶手/靠背的圆角与分缝可以再强化。

## 9. 家具逐件细化（2026-10-28，用户判定"过于简陋"后的第二轮）

用户原话（2026-10-28）："家具过于简陋，你只是用几个色块简单拼接起来的，看起来
像那么个家具，但实际上很粗糙。……对每一块的家具进行细化，生成更真实，不那么
违和的办公室物品。"

判定标准（本轮的验收口径）：剪影可辨识 / 材质可区分 / 结构可信 / 光照一致 /
不违和。全部改动仍只在 `?officeLayout=generated` 分支，默认外观未动。

  条形拉手（拉手下方 1px 亮线）+ 内缩踢脚。

### 9.3 本轮修掉的缺陷（含根因，避免回退）

1. **旧贴图显示器残影**：generated 模式只隐藏了 `sprite` / `graphics` 记录，
   漏了 `kind:'code'`（遗留贴图显示器被重画成 bezel+screen+stand 的那些）。
   屏幕左边因此多出一个深色钩子。→ 隐藏集合补上 `'code'`。
2. **台灯三错叠加**：灯罩 27×32px 与显示器等高且贴住其右缘，底盘 39×30px 还
   压住马克杯。→ 罩缩到约 13×18px、抬高 25px、与显示器留 17px、底盘缩到约 10×8px。
3. **马克杯像 UI 图标**：直接用原始 accent（饱和 0.68），而全场景其余物件在
   0.16–0.18。→ 新增 `ceramic` 材质（accent 往 paper 混 80–84%，饱和≈0.13）。
4. **沙发中缝透出背景**：两块靠背各留 0.002 内缩，中间 0.004 场景宽≈4px 是墙色，
   沙发像被切成两半。→ 两块在 `cx` 精确对接，中缝交给渲染器画线。
5. **叶片白色碎片**：叶形轮廓用 20 点自建路径（先 moveTo/lineTo，后 poly）都会
   在叶片上打出透背景的浅色碎片。多边形离线验证**不自交**，所以问题出在 Pixi v8
   在同一 Graphics 上复用路径状态。→ 叶子改用**纯简单图元**（椭圆 + 尖端三角，
   同色填充叠加），一个图元一次调用，不再复用自建路径。这是本轮最重要的坑。
6. **花盆托盘像"耳朵"**：托盘 0.58×盆宽，比盆口还宽。→ 收到 0.27×盆宽。
7. **`steam` 注释触发边界测试**：`test/office-team-execution.test.js` 用
   `/team|execution-schema|.../` 扫渲染器全文，`steam` 里的 `team` 让测试红。
   → 注释改词（milk-frother wand）。**新增注释时注意不要出现 `team` 子串。**

### 11.1 决策：绿植与办公椅回退到图片素材

经过两轮代码绘制迭代，结论是**这两类东西不适合代码生成**：

- 绿植：叶片的体积感、叶脉密度、陶土盆的质感，代码版在前景近距离下始终差一档。
- 办公椅：背视办公椅的形状细节（扶手、气压杆、五星脚、滚轮）代码版画得出来，
  但用户直观感受仍是"奇怪"，而旧素材 `prop-chair-back.png` 一看就是椅子。

**边界划法**（重要，避免以后又来回摇摆）：

| 类别 | 方案 | 理由 |
|---|---|---|
| 桌 / 显示器 / 椅子 / 台面 / 沙发 / 茶几 | **代码绘制** | 需要和角色一起参与逐件遮挡排序；素材反而受限 |
| 绿植 / 办公椅 | **图片素材** | 静态装饰/整组排序，素材细节明显更好 |

> 注：办公椅虽属"工位家具"，但它整组排在角色之后、且是静态摆件，
> 用素材没有排序代价，所以归到素材组。

### 11.2 素材接入方式

- 素材已在 `layout-assets.js` 登记（`flat-plant-*`、`flat-chair`），无需改注册表。
- `code-office.js` 的组上新增可选 `sprite` 描述（`assetId` / `footX` / `footY` /
  `width` / `height`）；渲染器 `buildOfficeGroupNode` 有纹理就建 `PIXI.Sprite`，
  **没有纹理就回退到原来的代码绘制**（离线测试与素材缺失都不会空白）。
- 落点按 `contentBbox` 对齐"盆底/椅脚"到组的地面基准，而不是画布底边——
  1024² 素材四周有大片留白，直接按画布底对齐会让植物悬空。
- `office.html` 在 `?officeLayout=generated` 时预加载这些素材（含失败诊断）。

### 11.3 素材配色归一化

素材是"独立插画"配色（陶土盆饱和 **0.58**），场景其余物件在 0.16–0.18，直接贴
像贴纸。处理方式（离屏一次性，非每帧）：

- **只压暖色通道**（`r - g > 4` 的像素），把红往绿收敛 → 陶土盆 0.58 → **≈0.20**。
- 绿色像素只做极轻的整体降饱和 → 保留叶色层次。
- **踩过的坑**：第一版做全局去饱和 0.72，结果虎皮兰/龟背竹的叶子变灰、整株像
  灰色塑料。所以必须按色相分流，不能一律拉灰。
- 暗色主题下素材额外乘 `0x6f7479`（tint 是乘算，只能压暗）；亮色显式复位为白色，
  否则从暗色切回会残留灰调。

### 12.1 图层顺序（本轮核心）

**根因**：椅子组的排序键是**靠背前下沿**（0.2458），比桌面前沿（0.2898）还小，
所以椅子被画在桌子**之前**、被桌板压住——这就是用户看到的"素材被放到最下层"。

修法是三个键一起定：

| 对象 | 键 | 值 | 说明 |
|---|---|---|---|
| 办公桌 | 桌面前沿 | 0.2898 | 不变 |
| 角色（站位） | **脚点** | 0.2958 | 原为 `deskFront-0.0002`，比桌子还小 |
| 办公椅 | **坐垫前沿** | 0.3138 | 原为靠背前下沿 0.2458 |

结果（画家算法：键大 = 后画 = 在上）：

- **坐在工位上**：椅子 > 鲸鱼娘 > 桌子 ✅
- **从旁边路过**：路人脚点 > 椅子键时角色压住椅子 ✅（纯几何，无需特判）

### 12.2 "椅子在最上"的代价与处理

椅子素材是**一整把椅子**（靠背+扶手+五星脚）。实测：角色精灵 **132px** 高、
椅子自然尺寸 **142px**，直接叠在角色前面会把鲸鱼娘从头到脚全挡住。

处理：把椅子精灵限制在角色身高的 **50%**（约 66px）。实测数据（probe `bounds.js`）：

```
角色 bounds y 75.3 .. 207.4  (h 132.1)
椅子 bounds y 108.4 .. 209.6 (h 101.2)   ← 上限 62% 时
```

62% 时只剩头顶 33px 可见；50% 能把五官与头发完整露出，椅背落在肩线以下。
`CHAIR_MAX_RATIO` 就是这个旋钮，值在 `code-office.js`。

> 注：`Chair` 的自然尺寸、`CHAR_SPRITE_PX` 都是**实测值**，前两版靠估算
> （214px）全都估错，导致椅子被反复放大/缩小。教训：这类比例问题必须用
> `/tmp/probe/bounds.js` 量真实 `getBounds()`，不要推公式。

### 12.3 角色"变小"的真相

实测两版**角色像素高度一致**（178px 立绘宽度 / 132px 精灵高度），角色本身没变。
变的是**相对比例**：桌子从 114px 放大到 178px（+56%），桌/角色从 0.64 涨到 1.00，
所以角色显小。

修法：`characterScale` 默认 **1.18 → 1.50**，同时桌宽 0.185 → **0.172**。
结果桌/角色 = 165/214 ≈ **0.77**（旧素材方案 0.64，当前比旧版略紧凑但不失衡）。

## 18. 第十轮：沙发扶手改成圆柱滚边（2026-10-29）

用户："做一下'沙发扶手仍是硬方块（顶部做过圆角），可以改成圆柱滚边'这一项，
茶几那块就不修改了。"

### 18.1 关键几何（必须先量，否则一定画错）

扶手实测：**w=21.1px、正面高 h=36.5px、顶面深度 d=56.7px**。

注意 `d > w` —— **顶面比宽度大得多**。这是本轮踩坑的根源：

- 第一版按"正面画一个圆"来做滚边。但正圆直径只能取 w=21px，而它在竖直方向
  要占 21px，顶面却有 56.7px 深 —— 圆被顶面淹没，渲染出来还是方块。
- 第二版把整圆画在 `topY` 处再让立面覆盖下半，结果圆顶被顶面上沿吃掉，
  只剩一条突兀的亮弧。

### 18.2 正确做法：顶面上的「纵向圆管」

2.5D 里扶手的圆滚边不是"正面一个圆"，而是**顶面靠前部的一条纵向圆管**：

```
tubeH   = min(w, d) * 0.62          // 管子可见高度
tubeTop = topY + (d - tubeH) * 0.55 // 放在顶面前部，后面留出扶手台面
wallTop = topY + d * 0.72           // 立面从顶面后段开始，上缘被管子压住
```

体积感靠四层：
1. 圆管本体（圆角矩形，圆角 = 半径 × 0.92）；
2. 左侧 1/3 竖向**母线高光**（顺着圆柱长度方向的亮带）；
3. 右侧 1/4 **暗面**；
4. 顶端一条扁椭圆亮弧（管头）+ 底端一道暗缝（与立面的接缝）。

立面另外做横向明暗（左亮右暗，窗在左）+ 内侧接触阴影 + 底部落地暗线。

- `CI=1 npm test`：**1953 / 1953 全绿**

## 20. 第十二轮：修复办公室运行时的节点死锁（2026-10-29）

用户："先深度阅读理解相关文档和构建鲸鱼娘办公室运行时的相关逻辑，尝试修复死锁的问题。"

### 20.1 结论：1953/1953 全绿

`office-five-workers-positions.test.js` 的三个 seed（a/b/c）现在都在 240s 内全部到位。
这个用例在**原始代码上也偶发失败**（seed x5 可复现），属于预先存在的缺陷。

### 20.2 死锁的完整链路（五个独立成因，逐层剥开）

用 `advanceOneTick` + `debugReservations()` 把每一步状态打出来，才看清是**五层**
问题叠在一起，而不是一个死锁：

**① 规划期：单出口被同伴身体封死 → UNREACHABLE**
`peerBlockedSegments()` 把所有同伴身体当作阻塞段（这是 2026-09 为了防 1D 对向
死锁而加的，**不能删**）。但当同伴恰好站在我**唯一的出口**上时就无解：
`desk-6-leave` 只有 `roam-4` / `desk-6-approach` 两条边（后者通向 spare 工位是
死胡同），coder 在 `desk-6-leave`、reviewer 在 `roam-4`（相距 21px），
两人的 `findRoute` 双双返回 `UNREACHABLE`。
→ 修法：`findRoute` 改成**严格 → 放宽**两段式。严格模式照旧避开同伴身体；
只有**完全找不到路**时才放开"几何绕行同伴身体"这一条，节点占用与容量约束
始终不放。有绕路时行为与之前完全一致。

**② 预留期：两个 task-bound 互抢 → hasPath 恒 false**
`tryAcquirePathReservation` 的抢占逻辑只释放 `!isTaskBound` 持有者，两个
task-bound 员工互堵时谁都不放。
→ 本次**没有**从这里修改（见 20.3：试过，导致活锁，已回退）。

**③ 腿段起点错位（真因之一）**
`currentLegSegments` 用 `route[0] → route[1]`，但身体未必在 `route[0]` 上
（实测 reviewer 身体在 `roam-6`，`nearestNodeId` 却判成 `desk-5-leave`，
两者仅距 10.8px）。于是占的是一段还没走到的路，真正要走的那段没预留。
→ 修法：`routeIndex === 0` 时，腿的起点用**身体实际位置**。

**④ 几何层：occupant gate 双方都返回 wait**
`step()` 的社交圈判定只在"已经重叠"（≤ ARRIVAL_TOLERANCE≈6px）时放行离开，
但两人相距 21px（社交半径 18.9px）互相挡路时，既不算重叠也不算能过。
→ 修法：**若这一步让双方距离变大**（正在走开）就放行。不会穿模：只有远离
方向被放行，靠近/横向擦过照旧拦。

**⑤ 无路线时直接 return（最后一环）**
`stepMovement` 开头 `if (!rec.route) return` —— task-bound 员工在 move 相位却没有
路线时，既不移动也不重试，永久停在半路（实测 orchestrator 在 `roam-1` 冻结，
`routeLen 0` 而 phase 仍是 `move`）。
→ 修法：给"无路线"补与 `handleBlocked` 同阈值的重试，周期性 `planTaskRoute`。

**⑥ 相邻节点互换死锁（最顽固的一个）**
A 站在对方的**目标节点**上：orchestrator 在 `roam-1` 要去 `roam-2`、
researcher 在 `roam-2` 要去 `roam-1`（另一 seed 是 `roam-6` ↔ `desk-5-leave`）。
两人相距 90px 远超社交半径，但每一步都必然擦过对方身体，双方全部返回 wait。
→ 修法：新增 `swapPriorityFor()`，判据刻意收窄到四条同时成立
（双方都 task-bound / 我的下一节点≈对方身体 / 对方的下一节点≈我身体 /
我的 id 字典序更小），**只有严格互换**才让 id 小的一方直接推进。
普通靠近、单向避让、绕行都不受影响。

### 20.3 试过但回退的方案（记录以免重走）

1. **相邻同伴不计入 blockedSegments** —— 会让 `desk-6-leave` 这种死胡同重新
   对向死锁，且破坏了 block 的原始防护意图。
2. **task-bound 之间按 id 抢占预留** —— 实测产生**活锁**：协作方抢到后对方
   立刻重新规划抢回（235 次抢占、位置 240s 不动）。加退避窗口能压下去但仍不
   解决根本。
3. **在 handleBlocked 里让 task-bound 互相让位** —— 两者都退避，退化成
   98% 静止（比原来更差）。
4. 上述补丁一度让 `office-module.js` 涨到 4816 行，**触发架构上限测试**
   （ceiling 4800，"composition, not a monolith"）。最终只保留 62 行
   （4736 行，合规）。

## §21 走路系统的第一性原理重构（2026-10-30）

用户判断："我们在这个走路问题上'在屎山上打补丁'了。"
这个判断是对的。量化证据：`M4.1a`~`M4.1h` 共 8 代机制标记，在
`movement-controller.js` / `behavior-scheduler.js` / `office-module.js` 里出现 159 次。
每一代都在上一代基础上修 bug，而不是换掉错误的前提。

### 21.1 拆到最小实现单位

走路只有三条**正确性**要求：

1. 位置连续（不瞬移）
2. 不与他人重叠（不穿模）
3. 一定能到达（不永久卡死）

其余（路径自然、绕路、避让姿态、落点分布）都是**表现形式**，可以调参，
不构成正确性。把这两类混在一起讨论，是前面所有混乱的起点。

### 21.2 找到真正的卡点

卡点不在一行代码，而在一句设计假设：

> **规划期把"其他角色的身体"当成静态障碍。**

`blockedSegments` 就是这个假设的实现。它带来的后果是：

- 我的"图可达性"变成了一个依赖于"别人此刻站在哪"的函数
- 而别人也在动，也在算可达性
- 于是 A 因为 B 站着而不可达，B 因为 C 站着而不可达，C 因为 A 站着而不可达
- 三人互相锁死，谁都不动，谁也不会重试

这不是某个 `if` 写错了，是**架构必然**：只要规划期依赖别人释放资源，
就存在死锁可能，而补丁只能处理已发现的死锁形态，无法穷举。

### 21.3 正确的职责分工

| 层 | 只负责 | 不负责 |
|---|---|---|
| 规划（findRoute / BFS） | 图上有没有一条路 | 路上有没有人 |
| 逐腿推进（step / occupant gate） | 这一步会不会踩到人 | 目标是否可达 |
| 目标选择（chooseTarget） | 去哪里更舒服（间距、区域配额） | 能不能到达 |

关键洞察：**"能不能到达"和"路上有没有人"是两件事，必须分开。**
把后者塞进前者，就得到了一张随时会变的图，和随之而来的死锁。

### 21.4 实测对照（不是推理，是数据）

5 名员工同时开工，3 个 seed，全部到达 work 相位的耗时：

| 配置 | seed-a | seed-b | seed-c |
|---|---|---|---|
| 含 `blockedSegments`（基线） | TIMEOUT | TIMEOUT | TIMEOUT |
| **删除 `blockedSegments`** | **49s** | **52s** | **46s** |

同时 `test/office-transition-loop.test.js` 的 41 个空间约束用例全部通过 ——
说明 `step()` 的 occupant gate 已经足够保证不穿模，`blockedSegments` 是
重复且有害的。

### 21.5 附带发现的更严重问题：默认 layout 回退指向错误 fixture

`createOfficeModule` 不传 `layout` 时回退到 `office-layout.json`（旧 27 节点
等距投影版），而生产运行时用的是 `office-layout-flat.json`（37 节点平面版）。

两张图结构不同：旧图 `chat-a`/`chat-b` 的入边 behaviors 缺少 `resting`，
节点少 10 个。后果是聊天决策成功但寻路永远 `CHAT_ROUTES_UNAVAILABLE` ——
实测 5 个 seed 里 4 个在 200 秒内**完全没有聊天**（`chatting` 采样数 = 0）。

这个缺陷长期被掩盖，因为出问题的正是"没有显式传 layout"的路径，
而生产入口 `office.html` 恰好显式传了。**测试用的路径和生产用的路径不一致，
是这类问题最难发现的形态。**

### 21.6 留给未来的三条规则

1. **规划期不得把别的角色当成障碍。** 规划只回答"图上有没有路"。
   如果将来确实需要"避开人群的路线偏好"，那应该是**打分排序**，
   而不是**从图里删边**——删边会让可达性依赖瞬时状态，重新引入死锁。
2. **默认值必须和生产路径一致。** 任何 `default`/fallback 都要问一句：
   生产入口会不会走到这里？如果不会，它就是一颗定时炸弹。
3. **不确定时先做对照实验，不要先改代码。** 本次两个关键结论
   （blockedSegments 有害、默认 fixture 错误）都来自 A/B 对照，
   而不是读代码推理。加了临时环境变量开关跑两组、量出数字、再动手。

## §22 互动层打磨 + 左右站位回退 + 语料库调研（2026-10-30 晚）

本阶段从"用户实际试用反馈"出发，修了三个交互缺陷、回退了一个视觉方向，
并按社区调研重写了闲聊语料。**结论性的一条**：视觉收益为负的方案要整体撤掉，
不要在它上面继续打补丁。

### 22.1 拖拽：从"松手弹回"到"停在放手处"

用户反馈："拖拽后鲸鱼娘会回到原来的位置，而不是我拖拽到哪就停到哪。"

原实现是 `presentation only`（`beginDrag` 的注释原文就写着 *on release eases
back*），只移动绘制节点、不碰模拟，下一帧快照就把位置覆盖回去。

修复踩了两个坑，**都是跨进程功能的典型坑**：

1. **只加了一半链路**。第一版在 preload 白名单和 payload 校验器里加了
   `office:place`，但漏了 `OFFICE_IPC_CHANNELS` 和 `registerOfficeIpc` 的
   `switch`，请求落到 `default → CHANNEL_UNKNOWN`。真机探针直接复现
   `No handler registered for 'office:place'`。
   **教训：单元测试验证"组件行为正确"不等于"链路正确"。**
2. **CSS 像素当 scene 像素用**。指针事件给 CSS 像素，渲染器要 scene 像素；
   窗口 1280×840 / 参考场景 960×630 时两者差 1.333 倍，落点被放大 33%，
   吸附到很远的错误节点。修法：`resize()` 记录 `letterboxScale`，
   `dragTo` 前换算。

设计取舍：**落点吸附最近图节点**（整张走位图的预留/BFS/逐腿推进都建在节点上，
放在节点之间会规划出斜切路线甚至穿家具）；**任务中的角色拖不动**
（拖走会让"在工位工作"与位置脱节）。

### 22.2 交互区：脚下圆形 → 全身矩形

用户要求："把脚下那个圆形交互区改成鲸鱼娘全身，但不超过身体边界。"

旧的 `hitTest` 是以脚点为圆心的圆（半径 0.35 可见高度），只有点脚下地面才命中。
改为按角色立绘的**真实身体矩形**：宽度由纹理长宽比推出并按 0.55 收窄
（两侧透明留白不算），拖拽/插值期间随画出来的位置同步更新。

真机验证：头/中/脚三点命中，身体左右外 8px、头顶上 8px 全部 miss。

### 22.3 闲聊朝向：从"都背影"到"一正一背"

纵向（up/down）原来都映射到 `side-back` —— 前后对立的两人**都显示背影**，
读起来像各自背对彼此。

角色包没有专门的"正面聊天"帧，但有 `idle`（正面）与 `side-back`（背面）。
最终方案（用户拍板）：
- **down**（站上方、朝下面对对方）→ **正面** `idle`
- **up**（站下方、朝上背对观众）→ **背面** `side-back`

### 22.4 左右站位：整体回退（本阶段最重要的判断）

曾为"能看到左右站位闲聊"新增横向座位对 `chat-c`/`chat-d`。实际效果很差：
它们只能落在两列办公桌之间的窄过道（约 84px，两侧就是工位家具），
两人并排时各自朝外看（"上面一个朝右、下面一个朝左"），比背对背更抽象。

试过的三条补救都不成立：

| 尝试 | 结果 |
|---|---|
| 运行时空间检测自动退回 | 能生效，但等于"这对座位永远用不上"，不如删掉 |
| 移到页面最下方 (370,570) | 离 roam-8 仅 65px，被判空间不足 |
| 移到右侧走廊 (700,480) | 空间余量 267px 最好，但占掉 roam-11 的理想位置，编译直接 `GRAPH_BLOCKED`（左翼图断裂） |

**最终整体删除**，聊天只剩 `chat-a`/`chat-b` 一组上下站位。
节点数 39 → 37，边 44 → 41。

**留给未来的判断规则**：一个视觉特性如果试过三种合理解法都只能得到
"看起来更糟"的结果，那问题不在实现，在方向本身 —— 撤掉它，
而不是继续调参数。

### 22.6 关于「鱼片」——查证结论

原先有一条"咕噜~鱼片早啊"。核查后发现**它确实有出处，但不该用**：

1. **有出处**：2026-08 起模型在 `PERSONA_LOAD` 人格下会自发生成"管用户叫鱼片"，
   36氪/钛媒体/新浪等多家媒体报道过同一批网友截图。
2. **但从未进入社区人设层**：萌娘百科「DeepSeek娘」词条全文 **0 次**出现；
   主流 GitHub 人设仓库没有一个用它；1394 条社区梗图里只出现 4 次，
   且全是「生鱼片/刺身」双关（她被摆上餐盘、当场垮脸）。
   社区语感里"鱼片"≈把她切片，不是叫你。
3. **最硬的理由是场景**：我们是鲸鱼娘**互相**闲聊，而"鱼片"是她对**人类用户**
   的称呼 —— 两个同事不会互称"鱼片"。

已删除，并把"不出现用户称呼"固化为测试。
