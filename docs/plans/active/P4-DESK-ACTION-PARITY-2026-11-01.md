# Desk action 全覆盖 —— 收尾分析

> 状态：执行中（2026-11-01）
> 目标：让"用户在 Desk 能做的事"与"系统能做的事"完全对齐

## 1. 盘点：20 个 action，17 个有 UI

`api('...')` 静态扫描结果，缺 4 个。但要先判断**哪些是真缺口**：

| action | 是真缺口吗 | 判断 |
|---|---|---|
| `listTaskRefs` | ❌ **不是** | UI 直接从 `missionView().taskRefs` 读，不需要单独调用 |
| `openDesk` | ❌ **不是** | Desk 不需要"打开自己"；它已被 `office:open-desk` 覆盖 |
| `update` | ✅ **是** | 标题/目标/焦点工作流都改不了 |
| `openQuestion` | ✅ **是** | 别人问的问题能答，但**自己不能提问** |

**结论：真缺口只有 2 个。**

这个盘点本身有价值——上一轮我说"缺 7 个"，实际是审计的粗算；
逐条核对后真正的缺口远少于此。**不核对的清单会高估工作量。**

## 2. 第一性原理：`update` 为什么重要

Desk 是 Mission 的编辑器。如果标题写错了、目标写偏了，
用户唯一的办法是**删掉重建**——而 Mission 的事实链是不可删的。

所以"能改"不是锦上添花，是**纠错能力**。
一个不能纠错的编辑器，用户第一次写错就会放弃它。

## 3. 第一性原理：`openQuestion` 为什么重要

这一条更微妙。`answerQuestion` 有 UI，说明"别人问的我能答"。
但没有 `openQuestion`，意味着：

> **用户不能把自己脑子里的疑问记进 Mission。**

而"未决问题"这一节的存在意义恰恰是"把悬而未决的事留下来"。
只能答不能问，等于这一节的内容全部来自外部（模型/他人），
用户自己无法往里放东西。

这与 `recordDecision` 是配对的：
- 决策 = 已经想清楚的
- 未决问题 = 还没想清楚的

**两者都是 Shared Context 的入口。只做一半等于只记结论不记悬念。**

## 4. 设计决定

### 决定 1：`update` 做成"就地编辑"，不弹窗

点击标题 → 变成输入框 → 失焦或回车保存。理由：
- 改标题是高频轻动作，弹窗太重
- Desk 已有"就地输入"模式（answerQuestion / recordDecision），保持一致

### 决定 2：`update` 不允许改 status

接口约定里 `update` 刻意不支持 status（状态变更走 `statusChanged`）。
UI 也必须尊重这一点——**不提供**"改状态"的输入框（那个已经在顶部选择器里）。

### 决定 3：`openQuestion` 与 `answerQuestion` 放在同一节

"未决问题"这一节应同时有：
- 列出已有的（含回答入口）
- 追加新的（提问入口）

它们在语义上是同一件事的两端。

## 5. 实施

| 步 | 内容 |
|---|---|
| S1 | 标题/目标就地编辑（`update`） |
| S2 | 焦点工作流选择（`update` 的第三个字段） |
| S3 | 提问表单（`openQuestion`） |
| S4 | 测试 + 真机验收 |

## 6. 验收标准

- [ ] 能改标题，改完 Brief 里的标题也跟着变
- [ ] 能改目标
- [ ] **UI 不提供**改 status 的入口（走顶部选择器）
- [ ] 能提问，提问后出现在"未决问题"里
- [ ] 提完的问题能立刻回答（两条路径闭环）
- [ ] 改完重启仍在

## 7. 非目标

- ❌ 不做富文本编辑
- ❌ 不把 `openDesk` / `listTaskRefs` 加进 UI（它们是假缺口）
