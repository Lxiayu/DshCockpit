# P2.4 Companion Mode —— 第一性原理分解

> 状态：执行中（2026-11-01）
> 上游：`docs/product/product-roadmap.md` §P2.4
> 验收标准（路线图原文）：「Companion Mode 能把办公室收成常驻小窗，**不丢状态**」

## 1. 先澄清一个歧义：rail ≠ Companion

路线图的「关键文件」写的是 `office-rail.js` 扩展。核实后发现：

| | 现有 `office-rail.html`（186 行） | Companion Mode 要的 |
|---|---|---|
| 形态 | 主窗口内的**左侧竖条** | **桌面常驻小窗** |
| 职责 | 视图切换器（harness / work / office 三个 tab） | 把办公室收成一个可随时唤起的小窗 |
| 生命周期 | 跟随主窗口（`addChildView`） | 独立于主窗口，主窗口关闭后仍可存在 |
| 数据 | 无（只是按钮） | **要显示真实的办公室状态摘要** |

所以不是"给 rail 加个按钮"，而是**新建一种窗口形态**。

可复用的是 rail 的**位置语义**（贴边常驻）与 `aux-windows.js` 的窗口生命周期模式。

## 2. 第一性原理：Companion Mode 到底解决什么问题

用户在**不打开完整办公室**的时候，需要知道什么？

不是全部状态。用户切到别的应用工作时，只关心一件事：
**「有没有需要我处理的事」**。

这是第一性原理的落点。推导：

1. 用户不打开完整窗口 → 因为注意力在别处
2. 注意力在别处 → 只可能被**打断**值得的信息吸引
3. 值得打断的只有两类：**待你处理**（pending）与**任务完成/失败**
4. 其余信息（谁在走动、今天用量、Mission 全貌）都不值得打断

所以 Companion 小窗的**最小有用内容**是：
- 一个数字：待你处理的数量
- 一个状态：正在跑的任务数（0 时不显示）
- 点击 → 展开完整办公室

**这个推导决定了"不丢状态"的具体含义**：不是"小窗里能看到所有状态"，
而是"小窗如实反映那两个决定性数字，且展开后完整状态还在"。

## 3. 三种形态与状态保持

| 形态 | 触发 | 显示 | 数据来源 |
|---|---|---|---|
| **collapsed** | 常驻默认 | 待办数 + 运行数（极小窗） | office 快照 |
| **expanded** | 点击小窗 | 完整办公室（现有主窗口） | 同左 |
| **hidden** | 用户关闭 | — | — |

「不丢状态」的三个具体含义：

1. **窗口切换不重建渲染器**：collapsed → expanded 复用同一个 office view，
   不是"关掉再开"。否则会丢摄像机位置、选中员工、滚动位置。
2. **主窗口关闭后 Companion 仍在**：它是独立窗口，不随主窗口销毁。
3. **数据不因形态变化而重置**：快照推送是持续的，形态只是显示与否。

## 4. 关键设计决定

### 决定 1：Companion 是独立 BrowserWindow，不是 main 的子视图

理由：验收标准要求"主窗口收起后仍常驻"。子视图做不到这一点。

代价：多一个渲染进程。但它加载的是**极简页面**（一个数字 + 一个图标），
不是完整办公室——所以开销可控。

### 决定 2：collapsed 状态不加载 PixiJS

办公室渲染器（PixiJS）启动成本高。常驻小窗只显示数字，
**不应该**为此启动整个渲染器。

所以 collapsed 用独立的极简 HTML（`companion.html`），
expanded 才唤起主窗口的 office 视图。

### 决定 3：数据走已有的 office 快照推送，不新建数据通道

`office:state` 已经在推 `pending` 与 employees。Companion 需要的两个数字
都能从中派生：
- 待办数 = `pending.length`
- 运行数 = employees 中 `runtime` 处于运行态的个数

**不新建数据通道**——这符合 repo-map.md §2.1「事实作者唯一」。

### 决定 4：不做"迷你办公室渲染"

一个诱惑是"在小窗里也画个迷你办公室"。这会让 PixiJS 常驻，
与决定 2 冲突，且违反路线图「不做办公室视觉大改」。

小窗只显示**数字**。想看画面就展开。

## 5. 实施分解（4 步）

| 步 | 内容 | 验证 |
|---|---|---|
| **S1** | `src/companion-state.js` —— 纯函数：快照 → `{pendingCount, runningCount, hasAttention}` | 单测（无 IO） |
| **S2** | `src/companion.html` + preload —— 极简 UI | 静态契约测试 |
| **S3** | `src/aux-windows.js` 加 companion 窗口（贴边、置顶、无边框） | 单测（生命周期） |
| **S4** | 真机验收（截图 + 交互） | 探针 |

先 S1（纯逻辑）再 S2-S3（窗口），最后 S4——与白板同一节奏：
**数据先对，再谈窗口**。

## 6. 验收标准（路线图 + 本项目追加）

- [ ] 能把办公室收成常驻小窗（collapsed）
- [ ] 小窗显示真实的待办数与运行数
- [ ] 点击小窗能展开完整办公室
- [ ] **展开后不丢状态**（选中员工、视图模式保持）
- [ ] 主窗口关闭后小窗仍在
- [ ] 0 待办时不显示警示红（不制造假警报）
- [ ] Companion 不加载 PixiJS（常驻成本可控）
- [ ] 数据来源是已有 office:state，无新通道

## 7. 明确的非目标

- ❌ 不做迷你办公室画面渲染
- ❌ 不做 Live2D（路线图 Deferred）
- ❌ 不做多显示器定位（先支持主屏右下角）
- ❌ 不改主窗口的现有行为
