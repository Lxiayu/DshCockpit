# 第一部分：这个右栏到底要解决什么

## 1.1 提示词的原始要求（保留原意）

> 「有用，能高效地解决问题，同时又是在官方 harness 里不好直接做的/看不到和展现的。」

这句话是**判据**，不是愿景。它的含义是：

| 官方已经做得好的 | 我们**不做** |
|---|---|
| 对话流 | 聊天窗口 |
| 工具调用详情 | 执行日志 |
| 会话列表 | 另一个会话列表 |
| 单会话内的任务面板 | Agent Dashboard |

| 官方**没有**的 | 我们的机会 |
|---|---|
| 跨会话的"我在做什么" | Mission 层 |
| 决策为什么这么定 | 决策+理由 |
| 什么还没验证 | 假设/证据 |
| 三天后会爆的东西 | 未决问题 |
| 需要人拍板的事集中一处 | 待办 |

## 1.2 ADR-0001 划的线（不可越）

> **右栏不是第二个聊天框。** 不做与官方 Harness UI 竞争的通用对话界面。

这条线决定了：右栏**只读执行、不重做执行**。

## 1.3 一句话定位（三个版本，需要你选一个）

| 版本 | 定位 | 隐喻 |
|---|---|---|
| **A. 遥控器** | 操作 Mission、发起工作、看进度 | 你握着它在驾驶 |
| **B. 仪表盘** | 集中显示需要你注意的一切 | 你看着它决定要不要介入 |
| **C. 档案柜** | 记录 Mission 的一切上下文 | 你回来时它还在那儿 |

**我的判断**：应该是 **A + B**，C 是副产品。
理由：C 单独存在时，用户不会主动去翻（这就是"50 轮做了什么"的病根）。

# 第二部分：设计思想的来源（不是我们拍脑袋）

## 2.1 「任务上下文不跨会话连续」

这是最初的痛点，也是整个产品的起点：

> 每次新会话，Agent 从零开始。你上周拍板的决定、这周确认的事实、
> 下周才能验证的假设——它们没有地方存。

Mission 层的存在理由就是这个。

## 2.2 「不能有两个事实作者」（铁律 1）

任何状态，凡是 Harness 会写的，我们**不能再写一份**。

这条铁律推导出：

| 数据 | 谁能写 | 我们怎么用 |
|---|---|---|
| 会话状态、工具调用 | Harness | 只读投影 |
| Team 成员/任务 | Harness（team 插件） | 只读投影 |
| 任务的 blockedBy/ready | Harness 算好的 | 原样透传，**不重新推导** |
| Mission 的目标/决策/假设 | **我们** | 唯一作者 |
| 会话绑定 | 本机 | 存 `.dsh/`，不进事件日志 |

**为什么重要**：如果我们也算 `ready`，两边算法一旦不同，
用户就会看到互相矛盾的状态——那时**没人知道哪个对**。

## 2.3 「不猜、不伪造」（贯穿全部实现）

具体表现（都是真机上验证过的）：

| 场景 | 错误做法 | 我们的做法 |
|---|---|---|
| 缺 `agentTeam` 投影 | 显示"0 个任务" | **完全不显示该区块** |
| Agent 说生成了文件 | 直接登记 | `fs.stat` + `realpath` 校验后才登记 |
| `turns > 0` | 显示"已完成" | 只报数字 + "不代表达到要求" |
| 验证通过 | 显示"已验证" | 显示"在快照 S 上用定义 D 通过"，会变 **stale** |
| `writeScopeWarnings` | 写"文件已锁定" | 写"**可能**存在冲突"（官方说只是提示） |
| 任务被阻塞 | 用当前任务的 ownerName | 查 `blockedBy` 表，显示**真正阻塞者** |
| plan-review 的 approve | 按选项顺序猜 | 用官方 `approve` 字段**命名匹配** |

## 2.4 「两层分类」（GPT 第三轮建议，我们核对后采纳）

> 如果所有东西都标红，用户会学会无视红色。

| 层 | 内容 | 判据 | 视觉 |
|---|---|---|---|
| **需要你决策** | approval / question / plan-review | **阻塞团队** | 红框 + 可操作 |
| **执行提醒** | 排队输入 / 权限风险 | **不阻塞**，但看不见会误判 | 中性底 + 彩色细线 |

## 2.5 「每个投影为一个明确的用户问题提供答案」

> 不要因为能拿到 21 个字段，就把 21 个字段全显示出来。

| 投影 | 回答的问题 | 用在哪 |
|---|---|---|
| `userQuestions` | 现在需要我回答什么？ | L1 待办 |
| `inbox` | 我交代的事排队了吗？ | L2 提醒 |
| `permissions` | 现在的执行风险？ | L2 提醒 |
| `agentTeam` | 团队在干什么？ | 团队任务 |
| `sessionStats` + `turnOutline` | 跑到哪了？说了什么？ | 交给团队 |
| `todos` | （未接）这个 Agent 的个人清单 | — |
| `plan` | （未接）是否在规划模式 | — |

## 3.1 当前区块清单（17 个，竖排）

> 「现在我们构建的右边栏和相关内容我很不满意，差的太多。」

具体表现：

4. **记录型表单占比过大**——用户不是来填表的

# 第四部分：问题诊断（第一性原理）

## 4.1 根本矛盾

**这个右栏同时服务三种完全不同的场景，却用同一套布局：**

| 场景 | 用户在做什么 | 需要什么 |
|---|---|---|
| **冷启动** | 刚创建 Mission，什么都不知道 | 「下一步做什么」 |
| **等待中** | 已交给团队，在等结果 | 「跑到哪了」 |
| **回归** | 离开几小时回来 | 「发生了什么变化」 |
| **沉淀** | 项目做完了要复盘 | 「当初为什么这么定」 |

**现在把它们全铺开了 = 每一种场景都被稀释。**

## 4.2 五个具体的结构病

### 病 1：空态占据主视觉

新 Mission 打开，用户看到的是：

```
还没有记录决策。
还没有记录发现。发现是"我们确认了 X 成立"…
还没有记录假设。假设是"我们暂时这么认为"…
还没有证据。证据是"凭什么相信这个结论"…
还没有未决问题。
还没有工作流。
还没有关联任何执行。
还没有登记产物。
```

**八句话在教概念，不是在帮用户做事。**

### 病 2：表单密度过高

决策=2 输入框、发现=2、假设=2、证据=3、未决问题=1、
工作流=1、关联执行=2、产物=2、交给团队=1。

**11 个输入框同时摊在用户面前。** 而用户此刻可能只想看一件事。

### 病 3：没有主次

「需要你决策」和「诊断按钮」在同一个视觉层，
虽然前者有红框，但用户要滚过 10 个区块才能到后者。

### 病 4：进步无法累积

用户填了决策，它躺在第 9 个区块里。**下次打开时它还在第 9 个区块，
和第一次一样难找。**

### 病 5：Mission 与 Harness 的关系不直观

「交给团队」在第 3 个区块，但用户不知道：
- 我现在看的是 Mission 还是会话？
- 这个 Mission 对应哪个会话？
- 切到 Harness 会看到什么？

# 第五部分：候选方案（需要你选）

## 方案 A：场景驱动（推荐）

**核心：右栏不是"一个页面"，而是"四种场景的四个视图"，自动切换。**

```
┌──────────────────────────────────┐
│ 调研 Agent Team 前沿      [active]│
├──────────────────────────────────┤
│                                  │
│   ← 这里根据场景自动变化 →        │
│                                  │
└──────────────────────────────────┘
```

| 场景 | 触发条件 | 显示什么 |
|---|---|---|
| **冷启动** | Mission 无决策/无产物/无绑定会话 | 大输入框「告诉团队要做什么」+ 目标确认 + 一句"或者先记录你要解决的问题" |
| **等待中** | 有绑定会话且 `turns` 在增长 | 进度 + Agent 最近回复 + 「继续交代」输入框。**其他全折叠** |
| **回归** | `lastSeenAtMs` 早于 1 小时且期间有事件 | 时间线：发生了什么 + 需要你决策的 + 本次新增 |
| **沉淀** | Mission 状态 = completed 或用户主动查看 | 完整档案：决策链、假设、证据、产物 |

**优点**：每个时刻只显示一件事，用户永远知道该看哪。
**缺点**：自动切换可能"猜错"用户意图，需要手动切换入口。

## 方案 B：三段式（保守）

**核心：保留所有区块，但分成三个 Tab / 三个折叠组。**

```
[现在] [团队] [档案]
```

| Tab | 内容 |
|---|---|
| **现在** | 待办 L1 + 交给团队 + 进度 + 离开期间 |
| **团队** | 团队任务 + 关联执行 + 实时状态 |
| **档案** | 目标/边界/决策/发现/假设/证据/未决问题/工作流/产物/Brief |

**优点**：用户可控，不会有"猜错"。
**缺点**：仍然要切 Tab；380px 里 Tab 占空间。

## 方案 C：时间流（激进）

**核心：放弃区块，改成一条按时间倒序的事件流。**

```
09:41  ✓ Agent 完成调研，报告在 docs/report.md
      [查看] [登记为产物]
09:20  ⚠ 需要你决定：用哪种研究方法
      [实证] [文献] [混合]
09:05  你：先调研 Agent Team 的前沿方案
08:50  创建 Mission「调研 Agent Team 前沿」
```

**优点**：最像"人在做事"的方式；天然解决"进步无法累积"。
**缺点**：
- 与"记录型表单"冲突（决策/假设不是事件，是状态）
- 需要完整事件流存储（我们目前是状态投影，不是事件流）
- 会退化成"第二个聊天框"（触 ADR-0001 红线）

## 方案 D：分层抽屉（最省事）

**核心：默认只显示 3 个区块，其余全部收进"展开全部"抽屉。**

```
⚠ 需要你决策 (1)
交给团队 [输入框]
✓ 团队运行正常
─────────────────
[展开全部 (14)  ⌄]
```

**优点**：改动最小，立刻可用。
**缺点**：本质还是"藏起来"，没解决信息架构。

# 第六部分：我的建议

## 6.1 推荐 A（场景驱动），但要加一个"手动兜底"

自动切换的状态机：

```
无绑定会话  ──交给团队──→  等待中
     ↑                      │
     │                  有需要决策的事
     │                      ↓
     └────── 回归 ←──── 回归触发
```

**关键补充**：顶部永远有一个手动切换（`[现在] [全部]`），
这样自动猜错时用户能自己找回。

## 6.2 无论选哪个，都应该做的四件事

### ① 消灭空态堆叠

现在 8 句话在教概念。改法：

```
还没有记录任何东西。
[记录一条决策] [记下一个发现] [记下一个假设]

或者：先告诉团队要做什么 →
```

**一句话 + 三个入口**，而不是八段解释。

### ② 表单按需展开

不要 11 个输入框同时摊开。规则：

- 区块**有内容**时：显示列表 + 一个小 `+` 按钮
- 点 `+` 才展开输入框
- 区块**空**时：不显示区块本身，只在"记录"入口里出现

### ③ 视觉优先级要拉开

| 层 | 视觉 |
|---|---|
| 需要你决策 | 红框、可操作按钮、永远置顶 |
| 正在发生 | 紫色/中性，带进度 |
| 记录档案 | 灰色、折叠、默认收起 |

### ④ Mission ↔ Harness 关系要显式

现在只有一句「在 Harness 中查看这个 Mission 的执行 →」。
应该改成：

```
这个 Mission 正在用会话 sess-h-cfa44aa 工作
[切到 Harness 看执行]  [换一个会话]
```
