## 记录目的

### 关键事实

1. Harness 提供的是工具、Agent 生命周期和子代理 provider，不提供固定的“编码 Agent”“搜索 Agent”等业务角色名单。
2. Standard Web Profile 默认工具主要覆盖文件/代码、网页搜索、子代理协作、规划、后台任务和用户提问。
3. Agent 生命周期状态只有 `idle` 和 `running`；`finished`、`warning`、`error` 等办公室状态需要由产品层根据 Runtime 事件派生。第一版不把常驻员工显示为 offline。
4. `subagent/start` 和 `subagent/end` 可提供真实子代理的 `runId`、Session ID、provider 和终止原因。
5. `subagent/descriptor` 只有 `mode`、`provider`、`label` 等身份信息，没有业务角色字段。
6. `spawn`、`fork`、`codex`、`claude-code` 是执行后端，不等同于办公室员工角色。

以上是 Harness 原生事实的范围。`eventId`、`sessionEpoch`、Office snapshot/resync 以及办公室角色和本地行为，均属于 DshCockpit 适配层或产品层；不能在实现中假定它们由 Harness 直接提供。

## 已确认决策

### 决策 1：第一版采用 4 名常驻员工

四名员工固定使用以下稳定 ID：

| 稳定 ID | 中文名 | 主要职责 |
|---|---|---|
| `orchestrator` | 总控员 | 接收任务、拆分任务、派遣和汇总子代理 |
| `researcher` | 研究员 | 搜索网页、阅读资料、整理外部信息 |
| `coder` | 编码员 | 编写代码、修改文件、运行命令 |
| `reviewer` | 审查员 | 运行测试、检查修改、反馈问题 |

工具亲和只是职责和行为参考，不是第一版的硬权限隔离。一个真实 Harness Agent 可能同时搜索、编码和测试。

### 决策 2：常驻员工与真实 Runtime Agent 分层

办公室员工始终是“在岗”的本地视觉实体，没有任务时也可以闲逛、聊天和休息，不显示为离线，不调用 LLM，不消耗 Token。

推荐的分层模型：

```text
ResidentEmployee
  ├─ 稳定身份、角色和视觉行为
  ├─ 本地闲逛、聊天、休息模拟
  └─ RuntimeBinding（可选）
       └─ 真实 Harness Agent / 子代理 Session
```

运行状态与在岗状态分开：

```text
presence: present
runtime: unbound | idle | running | attention
activity: roaming | chatting | resting | working
movement: stationary | moving | arriving | leaving
```

### 决策 3：使用 DshCockpit 侧边绑定表

不修改 Harness 原始 Session Log，由 DshCockpit 单独维护办公室绑定数据：

```text
Runtime Session ID -> Office Binding -> employeeId
```

绑定记录至少包含：

```text
sessionId
employeeId
bindingSource: root | manual | heuristic
confidence
boundAt
releasedAt
```

绑定规则：

1. 主 Harness 会话默认绑定到 `orchestrator`。
2. 子代理收到 `subagent/start` 后登记真实 Session ID。
3. 办公室明确派遣的任务，使用用户选择的员工进行绑定。
4. 模型自行创建的子代理，初始可以处于待归类状态。
5. 根据 `tool/call` 和任务描述进行的角色推断只能作为 fallback，不能覆盖用户确认的绑定。
6. `subagent/end` 后释放运行绑定，员工回到在岗空闲状态，并保留最近任务记录。

### 决策 4：办公室状态必须由真实 Runtime 事件驱动

主要映射关系：

| Runtime 事实 | 办公室表现 |
|---|---|
| Agent `running` | 员工走向工位并工作 |
| Agent `idle` 且无任务绑定 | 员工闲逛、聊天或休息 |
| `tool/call` | 显示搜索、编码、执行命令等具体活动 |
| `tool/result.error` | 进入注意或错误表现 |
| `turn/end.reason = completed` | 完成表现后回到日常活动 |
| `subagent/end` | 结束当前绑定并回到在岗空闲 |
| Agent 被销毁或 Runtime 不可达 | 保留常驻员工在办公室，交由 sync 层显示同步异常 |

### 决策 5：并发任务使用一个动态“协作者”席位

办公室不为每个并发 Session 无限复制角色。固定保留四名常驻员工；当已有员工都在处理任务，或出现无法明确归类的额外 Runtime Session 时，最多增加一个动态的 `collaborator` 席位。

协作者席位的规则：

1. 协作者是一个产品层的临时员工实例，不是新的固定业务角色。
2. 协作者绑定一个真实 Runtime Session，并显示该 Session 的当前活动和任务摘要。
3. 同时出现更多未归类或同类并发 Session 时，不再继续创建视觉实体，而是在协作者席位显示任务数量或排队信息。
4. 协作者任务结束后，席位回到空闲状态，可被下一个 Session 复用。
5. 协作者使用统一的 DeepSeek 娘外观和中性动作，不根据 provider 名称伪装成编码员、研究员或审查员。
6. 具体角色一旦由用户明确绑定，优先使用对应的四名常驻员工；协作者只承担额外或暂时无法归类的任务。

### 决策 6：协作者复用基础角色视觉

协作者暂不制作独立角色资产，直接复用四名常驻员工共用的 DeepSeek 娘基础形象。协作者身份通过名称、状态徽标、任务摘要和临时席位位置表达，不通过新的服装、配色或动作资产表达。

### 决策 7：空闲时自动漫游和社交

四名常驻员工在办公室打开后立即进入本地行为模拟，不等待 Harness 对话。空闲行为包括缓慢漫游、短暂停留、转身、休息，以及偶尔与另一名员工靠近并聊天。聊天和其他日常行为只使用预定义的本地动作，不调用 LLM，也不消耗 Token。

真实 Runtime 任务拥有更高优先级：员工被绑定并进入 `running` 后，暂停本地漫游，走向工位并由 Runtime 事件驱动工作表现；任务结束后执行短暂完成动作，再解除绑定并恢复漫游。

第一版行为引擎使用导航点、路径段和简单占位检测，不引入物理引擎或复杂寻路。每名员工独立运行本地状态机，目标点按时间和稳定随机种子定期更新；同一时间最多一组员工进行聊天，以避免场景拥堵。办公室页面不可见或关闭时暂停模拟，重新打开后恢复。

### 决策 8：六工位向右下方小幅偏移

办公室主体采用中央 `2 x 3` 六工位布局，但整体锚点相对场景中心略微向右下方移动，为左上方预留后续家具和装饰区域。偏移必须保持克制：角色活动区仍然是第一视觉重点，不能因家具预留而把人物推到边缘或压缩通道。

六工位的相对职责保持不变：四名常驻员工、一个协作者席位和一个备用/会议席位。桌子和工位入口保持稳定，左上方家具区只作为未来可插入的场景层，不参与当前员工绑定。

### 决策 9：角色素材使用统一脚底运动基线

所有状态图和行走帧保持统一画布尺寸，并记录角色实际可见边界和脚底锚点。脚底锚点是运行时定位和逐帧动画的共同基线：向左、向右、向上、向下行走以及转向时，脚底必须保持连续，不得因为透明边距或绘制姿势变化产生上下跳动。

角色显示尺寸以可见角色区域为基准，而不是以整张 PNG 画布为基准。桌子、电脑等场景物体保持独立图层，不参与角色素材的缩放和锚点计算。

### 决策 10：脚底锚点必须贯穿整段移动

统一锚点不仅用于角色初始落位，也必须贯穿“站起、行走、转向、到达目标点、停下”的整个动画过程。角色节点的场景坐标代表脚底接触地面的点；四帧行走图只能替换节点内部的图像内容，不能改变节点的定位基线。

具体约束如下：

1. 同一方向连续行走时，四帧图片的脚底 `y` 坐标必须一致；左右脚步交替只能改变腿部形状，不得改变整个人物的垂直位置。
2. 向左或向右移动时，角色的脚底应沿一条水平线移动，禁止出现由透明边距、画布裁切或帧间内容高度差导致的上下跳动。
3. 向上、向下行走和转身允许改变身体朝向，但脚底接触点仍以同一锚点规则计算；转向不通过销毁并重建角色节点完成。
4. 到达工位或公共导航点后，先完成最后一个位移过渡，再切换到站立/工作/休息姿态，避免停下瞬间“吸附”到另一条高度。
5. 素材验收以像素透明边界和锚点标注为准；运行时不得为单帧图片增加临时 `top` 修正值。若素材脚底不齐，应在素材预处理阶段修正，而不是在办公室渲染层打补丁。

第一版运行时采用“场景节点锚点 + 图片内部锚点”的两层模型：场景节点只负责脚底位置和移动插值，图片元素通过 manifest 中的 anchor/visibleBounds 对齐。这样 CSS 位移、Canvas 绘制或未来的其他渲染后端都共享同一套定位契约。

脚底素材验收阈值已确认：四帧行走图在统一画布和统一缩放基准下，脚底接触点的源图像坐标误差不得超过 `±1px`。预处理脚本应先检测每帧的透明边界和脚底候选点，再通过透明边距调整或画布内平移完成校准；若无法在不裁切可见角色的前提下达到阈值，则该素材标记为不合格并阻止进入角色包，而不是由运行时接受异常帧。

### 决策 11：manifest 使用源像素锚点，运行时负责比例换算

角色包 manifest 以统一源画布为坐标系保存锚点和可见边界，优先使用绝对像素值，不直接把经过窗口缩放后的 CSS 坐标写回素材配置。推荐契约如下：

```json
{
  "canvas": { "width": 2508, "height": 2508 },
  "anchor": { "x": 1254, "y": 2350 },
  "visibleBounds": {
    "x": 620,
    "y": 180,
    "width": 1260,
    "height": 2050
  }
}
```

运行时根据角色的目标显示尺寸计算统一缩放因子，再将源像素坐标换算为 CSS 像素或 Canvas 坐标。所有状态图和行走帧共享同一源画布与 anchor；窗口尺寸变化只重新计算显示比例，不重新测量或修改脚底锚点。除非素材本身经过版本化校准，否则不允许在页面 CSS 中覆盖 manifest 的定位数据。

### 决策 12：素材校准采用自动检测与人工覆盖并行

素材预处理默认自动分析每帧的透明边界、底部连通区域和候选脚底接触点，并将检测结果与四帧之间的差异写入校准报告。由于发丝、裙摆、阴影或生成图像残留都可能干扰自动判断，manifest 允许提供人工确认的 `anchor` 覆盖值；一旦存在覆盖值，它就是该角色包的最终定位依据。

校准流程固定为：

1. 自动检测并生成候选 anchor、visibleBounds 和逐帧差异。
2. 检查四帧脚底误差是否满足 `±1px` 阈值。
3. 检测不可靠或超出阈值时，由素材制作者在 manifest 中填写人工 anchor，预处理器据此重新校准透明边距。
4. 重新校准后仍无法满足阈值，或会裁切可见角色时，报告失败并阻止角色包进入运行时。
5. 校准报告保留源文件、检测值、覆盖值、最终值和失败原因，便于之后追溯素材变更。

### 决策 13：行走帧节奏先按 1 秒，并保留可调参数

第一版行走动画暂定每帧播放间隔为 `1 秒`，用于建立一个容易观察脚底基线、位移和转向问题的初始节奏。该值属于角色动画配置，不属于渲染器的固定常量；后续可以按实际观感调整为更短或更长的间隔，而不改变移动状态机和路径逻辑。

四个方向的动画序列采用可变帧数设计。第一版每个方向提供 4 帧，但运行时只依赖 manifest 声明的有序帧列表，不假设固定为 4 帧。后续增加起步、收步、转身或中间姿态帧时，只需更新角色包资源和帧时长配置即可：

```json
{
  "animations": {
    "walk-left": {
      "frames": ["left-01.png", "left-02.png", "left-03.png", "left-04.png"],
      "frameDurationMs": 1000,
      "loop": true
    }
  }
}
```

若不同帧需要不同停留时间，manifest 可进一步将 `frames` 声明为带有 `src` 和 `durationMs` 的对象列表；在没有单帧时长时，统一继承动画级别的 `frameDurationMs`。增加帧数不得改变脚底 anchor、角色节点尺寸或路径移动速度，动画播放与场景位移保持相互独立。

### 决策 14：移动速度使用场景比例单位

角色移动速度不使用固定 CSS 像素/秒，而使用相对于办公室场景尺寸的比例单位（例如场景宽度的百分比/秒）。渲染器在每次布局计算时将该速度换算为当前视口下的 CSS 位移速度，因此窗口放大或缩小时，角色的移动观感保持相近，不会因为像素密度变化而突然变得过快或过慢。

窗口尺寸变化期间遵循以下规则：

1. 角色的逻辑位置始终保存为场景比例坐标，脚底 anchor 不随窗口变化重新测量。
2. 正在执行的路径段根据新的场景尺寸重新计算剩余距离和 CSS 过渡时长，保持比例速度连续，不瞬移到新目标点。
3. 角色显示尺寸与场景坐标同时按新比例更新，图片内部 anchor 继续使用 manifest 的源像素值换算。
4. 如果窗口短暂不可见或进入后台，暂停本地模拟时钟和帧播放；恢复后从当前逻辑位置继续，不通过补跑时间造成跳跃。

第一版只需暴露一个全局默认速度和少量行为覆盖值（漫游、聊天靠近、前往工位），不把速度散落在 CSS 或具体角色资源中。这样后续增加帧数、替换素材或改变窗口布局时，移动参数仍然独立可调。

### 决策 15：角色显示比例以可见高度为基准

为解决角色过小的问题，第一版将 DeepSeek 娘的实际可见角色高度暂定为场景可视高度的 `10%–12%`，初始默认值取区间中值。这里的“可见高度”根据 manifest 的 `visibleBounds` 计算，不使用 2508 x 2508 PNG 的完整透明画布作为缩放基准。

显示比例规则如下：

1. 所有状态图和行走帧使用同一目标可见高度，确保切换姿态时人物不会突然变大或变小。
2. 根据当前场景可视高度计算源像素到 CSS/Canvas 像素的统一缩放因子，图片内部 anchor 与 visibleBounds 同步换算。
3. 角色尺寸配置保留全局默认值和角色级覆盖值，但不允许单独为某一帧设置尺寸。
4. 在极端窗口尺寸下增加最小和最大显示尺寸保护；保护只限制最终显示尺寸，不改变逻辑位置、脚底锚点或移动速度的比例定义。
5. 工位、聊天距离和导航点的间距均以角色显示尺寸为参考校验，避免角色放大后互相重叠或无法通过通道。

### 决策 16：Agent 状态采用四层模型

办公室不把所有状态压缩成一个枚举，而是拆成四个相互独立、由运行时组合解释的维度：

```text
presence
  present

sync
  healthy / stale / resyncing

runtime
  unbound / idle / running / attention / completed / failed

activity
  roaming / chatting / resting / working / thinking / celebrating

movement
  stationary / moving / arriving / leaving
```

`presence` 表示员工是否仍作为办公室实体存在；`runtime` 表示真实 Harness Session 的事实或派生结果；`activity` 表示员工当前执行的本地或任务行为；`movement` 表示目标点移动过程。动画控制器根据这些维度组合选择动画，不允许业务事件直接强制替换图片。

示例：

```text
runtime=idle + activity=roaming + movement=moving
  → 方向行走动画

runtime=running + activity=working + movement=stationary
  → 工位工作动画

runtime=completed + activity=celebrating + movement=stationary
  → 完成庆祝动画
```

该模型保证常驻员工无任务时仍可处于 `presence=present`，并允许“正在前往工位”“任务已完成但仍在庆祝”等过渡状态被准确表达。

### 决策 17：状态优先级由 Runtime 事实到本地闲置行为递减

当多个事件或行为候选同时存在时，按以下顺序决定员工的有效行为和动画：

```text
running / attention
  > 用户明确指令
  > completed / failed 短暂展示
  > roaming / chatting / resting
```

具体规则：

1. 常驻员工始终保持 `presence=present`；同步异常通过独立的 `sync` 层表达，不切换为 offline。
2. `running` 或 `attention` 优先于漫游、聊天和休息，员工应中断当前本地行为并前往工位。
3. 用户在办公室发出的明确派遣或控制指令优先于本地模拟行为，但不能伪造 Runtime 已经完成或失败的事实。
4. `completed` 和 `failed` 是短暂的结果展示阶段，可以在新任务到达时被抢占；没有新任务时播放完过渡后恢复本地行为。
5. `roaming`、`chatting` 和 `resting` 只在没有更高优先级 Runtime 或用户指令时运行。

状态机必须保留被中断行为的原因和恢复策略，避免任务结束后直接跳回旧目标点；通常应重新选择一个安全导航目标，再恢复漫游。

### 决策 18：状态切换由 Transition Controller 统一编排

员工不直接从一个最终状态硬切到另一个最终状态，而是由独立的 Transition Controller 编排中间阶段。第一版至少支持以下过渡链：

```text
漫游
  → 停止 / 转向
  → 前往工位
  → 抵达
  → 坐下 / 开始工作

工作
  → 完成或失败展示
  → 起身
  → 离开工位
  → 重新选择漫游目标

聊天
  → 结束聊天 / 分开
  → 前往任务目标
```

这些阶段是行为编排内部的过渡，不额外膨胀 Runtime 业务状态枚举；对外仍通过 `activity` 和 `movement` 表达当前可观察行为。Transition Controller 负责锁定当前目标、处理到达判定、触发动画切换和清理临时动作，并保存中断原因。

过渡可被更高优先级事件抢占：收到 `running`、`attention` 或用户明确指令时，立即停止低优先级过渡并重新规划目标；`sync=stale/resyncing` 不直接抢占或改变员工行为。低优先级的完成庆祝、聊天和漫游不得阻止任务响应。抢占后不得复用已经失效的旧路径或旧聊天对象。

### 决策 19：事件来源按事实、指令和本地模拟分权

状态机不接受所有来源的事件平权写入。不同来源只能更新自己负责的状态维度：

```text
Harness Runtime 事件
  → 真实 runtime 状态、任务阶段、工具活动和错误事实

用户指令
  → 明确派遣、员工绑定、取消/中断等已验证控制意图；未验证的控制只能作为禁用的预留能力

本地行为时钟
  → 漫游、聊天、休息、目标选择和动画推进

窗口生命周期 / 尺寸变化
  → 模拟暂停恢复、渲染器重建和布局比例更新
```

本地行为时钟不得伪造 `running`、`completed`、`failed` 或工具调用；渲染器也不得根据图片播放结果反推 Runtime 状态。用户指令可以改变目标和绑定意图，但不能把尚未收到 Runtime 证据的任务标记为已完成或失败。窗口隐藏只暂停本地模拟和渲染，不改变真实 Runtime 状态。

### 决策 20：Office 适配层必须补齐幂等、顺序和会话代际信息

Harness 原生事件只保证 `type/seq/time/data`。为防止通信重复、延迟或 Runtime 重启造成角色状态乱跳，Office State Adapter 在进入状态机前统一补齐以下字段；其中 `eventId` 和 `sessionEpoch` 是 Adapter 派生字段，不是 Harness 原生字段：

```text
eventId
sessionId
sessionEpoch
sequence
eventType
payload
```

处理规则：

1. 同一 `eventId` 只生效一次，重复事件必须幂等处理。
2. 每个 `sessionId` 维护已处理的最大 `sequence`；旧序号事件直接丢弃，不能回写状态。
3. Runtime 重启后生成新的 `sessionEpoch`；旧代际事件不能覆盖当前代际的绑定或状态。
4. 事件缓存和去重范围以 Session 为边界，不能用全局序号混淆不同 Agent。
5. 被丢弃的重复或过期事件可写入诊断日志，但不得触发角色移动、动画切换或活动日志重复记录。

这套规则同时适用于根 Harness Session、真实子代理 Session 和动态协作者席位，保证视觉状态与当前 Runtime 事实保持一致。

### 决策 21：常驻员工不使用 offline，长时间空闲进入睡眠行为

第一版不提供“员工离线”这一办公室表现。四名常驻员工始终保持 `presence=present`，即使没有 Harness 对话、没有绑定任务或 Runtime 暂时没有新事件，也仍然是办公室中的在岗员工。

长时间没有任务时，员工通过本地行为调度从漫游或休息进入 `activity=sleeping`，表现为趴在工位或指定休息点睡着。睡眠是可被任务抢占的本地活动，不代表 Runtime 已停止、Session 已结束或员工不可用。

同步异常单独记录为：

```text
sync: healthy / stale / resyncing
```

同步异常只影响状态徽标、诊断信息和恢复流程，不改变员工的 `presence`，也不自动触发 offline 动画。对于仍绑定且尚未收到结束事件的运行任务，即使 `sync=stale`，也不能擅自让员工进入睡眠；应保留最后一个可信的任务表现，直到 Runtime 明确结束、解绑或重新同步。

### 决策 22：睡眠触发时间默认 5 分钟，并允许用户调节

员工连续无任务达到 5 分钟后，允许本地行为调度从漫游或普通休息进入 `activity=sleeping`。该阈值是办公室本地行为参数，不代表 Runtime 状态，也不改变员工的 `presence` 或 Session 绑定。

睡眠阈值应作为设置界面的可调选项持久化保存，并具备合理的最小值和最大值保护，避免设置为 0 导致角色刚打开就睡眠，或设置过大导致永远无法触发。设置修改后立即应用于未被 Runtime 任务占用的员工；正在工作、前往工位或执行完成/失败过渡的员工不因设置变更被强行切换。

### 决策 23：第一版睡眠默认回到个人工位

第一版暂不依赖沙发、休息区等额外家具素材。员工进入 `activity=sleeping` 前，默认回到自己的工位并播放趴在桌面上睡觉的角色动作；工位是当前唯一稳定、可验证的睡眠目标。

睡眠目标通过行为配置而不是状态机硬编码：后续增加休息区、沙发或其他家具后，可以为角色或办公室布局配置新的 sleep waypoint，而不改变睡眠触发条件、状态优先级或动画接口。如果目标点不可用，行为调度器回退到个人工位。

### 决策 24：本地行为采用带权重和冷却的决策点调度

员工的本地行为不在每一帧重新随机，而是在明确的决策点重新选择下一行为。决策点包括：抵达目标、休息结束、聊天结束、任务释放、睡眠结束以及窗口从暂停状态恢复。

调度器根据行为权重、员工稳定随机种子、最近行为记录和当前场景占用情况选择目标。第一版至少检查以下约束：

1. 漫游、休息、聊天和睡眠均为本地行为，不产生 LLM 调用或 Runtime 事件。
2. 每名员工使用稳定随机种子，避免每次打开办公室或每帧刷新都得到完全不同的行为序列。
3. 每种行为设置最短停留时间和冷却时间，避免角色原地抖动、频繁转向或连续重复同一动作。
4. 导航目标需要通过占用和安全距离检查；已被其他员工占用的目标应换选或排队。
5. 同一时间最多允许一组员工进入聊天行为，聊天对象必须在可达距离内，任务到达时立即结束聊天并释放双方目标。
6. 睡眠只在连续无任务达到设置阈值后进入，并且优先级低于任何 Runtime 任务或用户指令。

调度器只在决策点改变 `activity` 和目标，逐帧位置、方向和动画帧由 Movement Controller 与 Animation Controller 根据当前目标推进。这样行为选择的随机性不会污染渲染时钟，也不会导致角色移动不连续。

### 决策 25：空闲行为采用第一版默认权重

在员工尚未达到睡眠阈值、且没有 Runtime 任务或用户指令时，本地行为调度使用以下初始权重：

```text
roaming  60%
resting  25%
chatting 15%
```

权重只在行为决策点使用，不影响移动速度、动画帧时钟或状态优先级。它们作为办公室内部配置保留，后续可根据实际观感调整；第一版不要求用户单独编辑这些权重。连续无任务达到设置的 5 分钟阈值后，员工直接进入 `sleeping`，不再按普通空闲权重抽选。

### 决策 26：聊天采用最近邻配对和固定聊天点

聊天行为只从当前空闲、未处于过渡、未被其他聊天占用且通过冷却检查的员工中选择对象。调度器优先选择距离较近、近期未互相聊天过的员工，避免跨越整个办公室频繁穿行。

配对成功后，两名员工前往一组固定的聊天目标点，保持预设间距并互相朝向；聊天期间不再重新选择漫游目标。同一时间最多存在一组聊天，聊天结束后双方分别回到行为决策点。任一员工收到高优先级任务、用户明确指令或同步恢复要求时，立即结束聊天、释放聊天锁和目标占用，并重新规划各自路径。

聊天冷却和持续时间均为本地配置，不产生 LLM 对话，也不代表 Harness 中真的发生了 Agent-to-Agent 消息。未来如果 Runtime 提供真实协作事件，可以在不改变本地聊天机制的前提下叠加真实消息标记。

### 决策 27：移动目标采用语义节点与显式路径边

第一版使用 Waypoint Graph 管理办公室移动。节点保存比例坐标、用途标签、容量和安全距离；路径边明确两个节点之间是否允许直接通行。初始节点类型包括：六个工位入口、若干地面漫游点、聊天点和每名员工的睡眠目标。

行为调度器根据标签选择目标，Movement Controller 负责在图上查找路线并逐段推进，Animation Controller 根据当前路径段方向选择行走动画。三者通过目标和移动快照通信，不互相写入内部状态。

节点与边至少支持以下约束：

1. `tags` 限制节点适用的行为，例如 `roaming`、`chatting`、`sleeping`、`desk`。
2. `capacity` 和临时 reservation 防止多个员工同时占用同一工位、聊天点或狭窄通道。
3. 路径边可以被标记为不可通行或仅允许特定行为，避免角色穿过桌子、墙体或未来家具区域。
4. 路线搜索使用小规模图搜索，不在第一版引入物理引擎或复杂 A*；图规模扩大后仍可替换搜索实现而不改变行为接口。
5. 办公室布局、家具和休息区通过新增节点、边和标签扩展，不修改角色状态机或动画系统。

如果目标节点暂时不可用，调度器应换选同标签候选或进入短暂等待，不得瞬移到目标坐标。所有节点坐标使用场景比例值，窗口缩放时只重新换算显示坐标。

### 决策 28：工具调用使用通用工作动画和活动子标签

第一版不为搜索、编码、测试、命令执行等每种工具制作独立动画。Runtime 事件映射采用通用工作表现，具体工具类别作为活动子标签、任务摘要和详情面板数据保存：

```text
session/start 或 turn/start
  → 绑定员工，执行前往工位过渡

tool/call
  → 保持 runtime=running / activity=working
  → 更新工具类别、参数摘要和最近活动

tool/result.error
  → 更新 attention 或 failed 事实
  → 进入对应的短暂结果过渡

turn/end.reason=completed
  → 进入 completed 结果展示
  → 旧绑定进入 releasing，锁存 lastResult
  → 结果展示结束后按 FIFO 继续队列或恢复本地行为
```

工具类别不得直接创建新的 Runtime 顶层状态，也不得强制切换角色图片。未来增加专用动作资源时，可以在 Animation Controller 层根据活动子标签叠加，不改变 Runtime 事件契约。

### 决策 29：完成和失败的结果动画默认展示 5 秒

`completed` 和 `failed` 的 Runtime 事实写入活动记录并保留在详情面板中；角色上的庆祝、困惑或异常动作只作为短暂视觉展示。第一版结果动画默认持续 `5 秒`，结束后员工按 FIFO 处理排队任务，否则回到本地行为。显式紧急派遣可以抢占结果展示。

结果动画持续时间作为设置项开放给用户调整。设置改变只影响尚未开始或正在播放的结果过渡，不修改已记录的 Runtime 事实；新任务到达时仍可按状态优先级立即抢占结果动画。若用户选择极短时长，系统仍保留一个最小展示时间以确保动作不会被瞬间跳过。

### 决策 30：动画能力声明与分级回退并存

Character Runtime 根据角色包 manifest 声明的动画能力选择资源。对于已提供的专用动画，优先播放专用动画；对于暂时缺少的状态，按预定义回退链使用兼容的静态姿态、方向动画或轻量程序化微动，不因单个资源缺失而阻塞办公室运行。

第一版 DeepSeek 娘角色包仍以配齐主要状态和过渡素材为目标，回退机制只是资源制作期间和第三方角色包的保障，不是降低官方素材完整度的理由。建议优先补齐：

```text
四方向 walk cycle
idle / resting / sleeping
working
thinking / waiting
completed
failed / attention
chatting 或互相朝向的侧身姿态
起身、坐下、转向等过渡帧
```

manifest 需要区分“专用资源已提供”和“运行时允许回退”两种情况；运行时记录实际采用的资源来源，便于 Playground 和素材验收发现缺口。回退只能改变动画表现，不能改变 Agent 的 Runtime 状态、移动目标或事件记录。

### 决策 31：第一版状态到动画的基础映射

第一版 Animation Controller 使用以下基础映射，并遵循“专用资源优先、兼容资源回退、最后使用程序化微动”的顺序：

| 状态组合 | 首选动画 | 资源缺失时的回退 |
|---|---|---|
| `movement=moving` | `walk-{direction}` | 最近可用方向帧或静态方向姿态 |
| `activity=working` | `working` | working 静态图 + 轻微程序化微动 |
| `activity=thinking` | `thinking` | 侧身或 idle 姿态 |
| `activity=waiting` | `waiting` | idle 姿态 |
| `activity=sleeping` | `sleeping` | 趴桌/idle 静态姿态 |
| `activity=celebrating` / `runtime=completed` | `celebrate` / `jump` / `wave` | 短暂程序化强调效果 |
| `runtime=failed` / `runtime=attention` | `failed` / `warning` / `shake` | warning/error 静态图 + 轻微抖动 |
| `activity=chatting` | 侧身相向或聊天专用动画 | 两个方向静态姿态 + 聊天气泡 |

移动中的方向行走动画优先级高于普通 idle/working 静态图，但不会覆盖 `runtime` 事实；例如员工仍处于 `runtime=running` 时，前往工位阶段播放 walk，抵达后才切换 working。Animation Controller 记录最终选中的资源 ID 和回退原因，供 Playground、诊断日志和角色包验收使用。

## 动画方案评估（2026-08-29，历史评估，Superseded）

> 本节为 2026-08-29 的动画架构方案评估记录，尚未批准正式实现；相关取舍已由决策 32（扁平 2D 正交办公室）、决策 30/31 及五份 Character Runtime 规格冻结。保留仅作历史追溯，不作为实现输入。

用户提供的“PixiJS + Texture Atlas + Frame Animation + Character State Machine + Target-based Movement”报告，整体方向符合 Virtual Office 的长期目标，适合作为后续 `Character Runtime` 的候选主架构，但不能不加修改地直接落地。

### 可采纳部分

1. PixiJS 负责实时 2D 渲染，角色位置、速度、方向、动画状态和行为状态彼此解耦。
2. 角色素材经过透明边界、统一画布、脚底 anchor 和 atlas 处理后再进入运行时，不把 PNG 当作 DOM 图片轮播。
3. 移动使用目标点和 Waypoint Graph，第一版不引入物理引擎或 A* 寻路。
4. 先制作独立 Animation Playground，验证素材和过渡质量后再接入完整办公室。
5. Character Runtime 与具体角色包分离，角色包通过 manifest 注册动画能力和资源许可。

### 必须修正的部分

1. 当前 DshCockpit 不是 React 应用，正式架构应为 `Electron → office.html → PixiJS Renderer → Character Runtime`，不得假设已有 React 层。
2. PixiJS 只负责渲染和帧时钟，不承载 Runtime 绑定、Agent 业务状态或 IPC。状态归属、行为模拟、移动控制、动画控制和渲染器需要有明确模块边界。
3. 第一版可以使用 PixiJS Assets 加载单帧 PNG 作为 Playground 输入，完成素材校准后再生成 Texture Atlas；运行时应支持 atlas 和单帧资源两种来源，避免资源管线尚未成熟时阻塞验证。
4. 动画必须使用 Pixi ticker/`requestAnimationFrame` 的 delta time 驱动，不能用 `setInterval` 硬切帧。移动逻辑和动画播放都按经过时间计算，但互不绑定。
5. 报告中的 `offline` 不作为常驻员工的动画状态。办公室采用 `presence / runtime / sync / activity / movement / animation` 分层；Runtime 不可达只改变 sync，不改变常驻员工在岗表现。
6. 4 帧行走图是否自然必须通过 Contact、Passing、脚步间距和身体重心检查确认。PixiJS 不能修复源素材缺少中间态的问题；不合格素材需要补帧或重制。
7. 2508 x 2508 原图不能直接按原尺寸批量驻留在 GPU 中。素材预处理必须生成面向实际显示尺寸和高 DPI 的资源，并在 atlas 构建阶段检查纹理尺寸、内存占用和最大纹理限制。

### 与既有决策的兼容规则

行走帧间隔先按 `1 秒`作为可观察、可调的 Playground 初始值；它不是最终动作质量结论，也不覆盖未来通过实机验证得到的更合适帧率。后续可将默认值调整到更高帧率，但必须保持脚底 anchor、角色显示比例和移动速度契约不变。

### 当前建议的运行时分层

```text
Office Runtime
  ├─ Agent Binding / Runtime Events
  ├─ Local Behavior Simulator
  ├─ Movement Controller (target + waypoint)
  ├─ Animation State Machine
  ├─ Asset Resolver (manifest + atlas / PNG fallback)
  └─ PixiJS Renderer
```

这份评估只记录方案取舍，尚未批准正式实现。正式开发前仍需分别形成动画架构、状态机、移动系统、素材规范和 Playground 计划，并经过用户确认。

对照项目根目录的《Agent Office 产品设计总纲 v0.1》，当前已经确认的内容主要覆盖“员工是谁、如何绑定 Runtime、如何在场景中移动、角色素材如何对齐，以及动画采用什么技术路线”。以下内容仍需要在正式实现前继续讨论并形成契约。

### 已基本确认

- 产品定位：Virtual Office 是 Agent Runtime 的人格化可视化层，不是独立小游戏。
- 员工模型：4 名常驻员工 + 1 个动态协作者席位，常驻员工无任务时也在岗并本地漫游。
- Runtime 分层：本地员工实体与真实 Harness Session 分离，通过 DshCockpit 绑定表关联。
- 场景布局：中央 2 x 3 六工位，整体向右下方小幅偏移，左上方预留扩展区域。
- 角色资源：统一画布、visibleBounds、脚底 anchor、源像素 manifest 和素材校准流程。
- 动画路线：PixiJS Renderer + Character Runtime + Waypoint Movement + Animation Playground。

### 仍需优先讨论

1. **Agent 状态机契约**：确定 `runtime / activity / movement / animation` 的字段、优先级、合法转换、事件来源和超时处理，避免把 `working`、`walking`、`chatting` 等不同维度混成一个枚举。
2. **本地行为调度器**：确定漫游、停留、聊天、休息、转向和任务抢占的决策规则，包括随机种子、最短停留、同组聊天限制和页面恢复后的时间处理。
3. **Runtime 事件映射**：确定 Harness 事件到员工状态的完整映射，以及事件丢失、重复、乱序、Runtime 重启和 Session 结束后的恢复策略。
4. **交互模型**：确定点击角色后的信息面板、任务摘要、明确派遣、协作者排队提示、聊天气泡和键盘/无障碍行为；这些交互不能打断 Pixi 场景时钟。
5. **场景视觉与层级**：确定 Pixi 场景的背景、工位、角色脚底排序、遮挡规则、通道安全区、镜头边界和不同窗口尺寸下的视觉焦点。
6. **状态过渡设计**：明确站起、走向工位、停下、开始工作、完成庆祝、离开工位和恢复漫游的过渡动画及可中断规则。
7. **角色包生命周期与许可证**：确定角色包安装、激活、停用、更新、移除、版本兼容和第三方授权检查的运行时契约。
8. **MVP 验收与测试**：确定 Playground 的可接受标准、动画视觉回归、移动/状态机单元测试、Runtime 事件回放测试、窗口缩放测试和 reduced-motion 降级行为。

### 建议讨论顺序

```text
状态机契约
  → 本地行为调度
  → Runtime 事件与恢复
  → 状态过渡与动画映射
  → 场景层级与交互
  → 角色包生命周期
  → Playground 与 MVP 验收
```

总纲中的 IP 生态、社区市场、统计传播和自由布局属于后续阶段，不应阻塞第一版 Character Runtime 和基础办公室的设计。

## 视角方案评估（历史候选，已取代，2026-08-29）

参考用户提供的 Marvis 办公室截图，其画面更接近“固定三分之四俯视 + 物体视觉取舍”，而不是严格物理透视。截图同时强调桌面、显示器、椅背和角色识别，这在真实相机中存在视线冲突，因此 DshCockpit 需要先确定自己的艺术化视角契约。尤其要明确：所谓“看到显示器正面”和“看到椅子背部”不能只用相机位置推导，部分效果需要通过家具素材的朝向和遮挡规则主动实现。

当前候选方案：

1. **固定三分之四俯视（Marvis 风格参考）**：场景整体最容易容纳 2 x 3 工位，桌面和公共空间清晰，适合办公室总览；角色工作时更多看到背面或三分之四后侧，面部表现较弱，需要补齐与该投影一致的坐姿和行走素材。
2. **侧后方三分之四视角**：角色侧脸、桌面侧面和椅背更容易同时表现，人物个性更突出；但显示器正面可见度下降，六工位排布更容易互相遮挡，需要更严格的通道和层级设计。
3. **场景俯视 + 角色状态定向的混合方案**：办公室家具采用固定三分之四俯视，工作状态使用侧身/三分之四坐姿角色帧，漫游仍使用四方向行走帧。表现力最好，但必须为“场景投影”和“角色姿态投影”分别制定素材规范，不能把不同视角的图片直接拼接。

现有 DeepSeek 娘素材包含正面、侧面和背面行走帧，以及偏正面的 working 图，尚不足以证明三种方案中的任何一种可以直接进入最终产品。无论选择哪种视角，都必须先在 Animation Playground 中用同一套桌子、椅子和角色占位素材验证：脚底基线、坐姿遮挡、显示器可见区域、角色面部可读性和四方向移动是否一致。

视角确定后，以下内容才能冻结：工位朝向、角色工作帧的拍摄方向、walk-up/down 的屏幕深度含义、桌面和椅子的前后层级、家具投影规范、聊天时的相对朝向，以及后续图片资产的生成提示词。

### 视角修正结论（历史候选，已取代，2026-08-29）

用户指出强透视房间会让现有 2D 角色像贴纸一样穿帮，并增加路径、比例和遮挡控制难度。该判断成立，因此 GPT Image 生成的强透视概念图只保留为构图参考，不再作为最终场景投影候选。正式视角必须满足：无消失点、无按深度自动缩放、角色逻辑坐标可逆换算、家具和角色共享同一平面规则。

后续只比较适合 2D 素材的两种投影：

1. **扁平正交俯视**：场景平面接近地图视角，桌面和通道最容易拆成 2D 图层，路径控制最简单；代价是桌面、椅背和显示器正面的立体层次较弱。
2. **正交三分之四 2.5D**：使用固定角度的正交投影表达桌面、椅背和显示器层次，但取消透视缩放和真实摄像机深度；所有家具是同一投影下的 2D 精灵，角色仍以脚底 anchor 贴在统一逻辑地面上。代价是需要严格统一家具素材的投影角度、基线和遮挡元数据。

无论选择哪种投影，路径都在逻辑办公室平面中计算，再由固定投影函数转换到屏幕坐标；角色不会根据屏幕上的透视距离改变大小。`walk-up/down/left/right` 表示逻辑平面方向，不能直接把图片朝向当成真实 3D 相机方向。

### 视角方向收敛：优先采用扁平 Marvis 式 2D 办公室（已被决策 32 取代，2026-08-29）

进一步结合现有 DeepSeek 娘素材后，前文的“正交三分之四 2.5D”需要避免被理解为具有真实体积、透视纵深或动态摄像机的 3D 场景。对于全部由平面 PNG 组成的角色系统，更稳妥的方向是采用 Marvis 式的扁平 2D 办公室：使用固定的正交/等距构图表达桌面和椅背层次，但所有对象仍是经过统一投影规范绘制的 2D 精灵。

该方向的核心不是复制 Marvis 的素材，而是采用相近的空间表达原则：

1. 场景没有消失点，不按远近自动缩放角色或家具。
2. 每个对象通过固定的 footprint、anchor、layer 和遮挡元数据参与场景，而不是依赖真实 3D 深度。
3. 角色始终是贴在逻辑地面上的 2D 精灵，移动、碰撞和聊天距离都在二维办公室平面中计算。
4. 桌面、椅背、显示器正面等视觉关系可以通过分层绘制和局部遮挡实现，不要求它们符合真实相机的全部视线规律。
5. 角色之间的交互不使用可见像素轮廓做碰撞，而使用脚底附近的逻辑 footprint，避免头发、衣摆或动作帧造成误判。

因此，Marvis 式扁平 2D 方案是当前比“有体积感的 2.5D”更优的候选：它更贴合现有素材，路径和脚底 anchor 更容易验证，角色互相靠近时也更容易控制。代价是家具必须统一绘制风格，遮挡关系需要人工配置，场景不会提供真实 3D 的自由旋转或镜头效果。

### 决策 32：第一版采用扁平 Marvis 式 2D 正交办公室

第一版正式采用 `Marvis-inspired Flat 2D Orthographic Office` 作为场景投影和资产制作规范。办公室使用固定的扁平斜俯视构图表达桌面、椅背和工位关系，但不引入真实 3D 体积、透视缩放、动态摄像机或按深度改变角色大小。

第一版的硬约束为：

1. 角色、家具和装饰全部作为统一投影下的 2D 精灵处理。
2. 角色逻辑位置、移动路径、碰撞 footprint 和聊天距离都在二维办公室平面中计算。
3. 角色显示尺寸、脚底 anchor 和运动基线在整个场景中保持一致，不因屏幕深度或上下位置自动缩放。
4. 桌面、椅背、显示器和角色之间的前后关系由显式图层、footprint、layer 和遮挡元数据控制。
5. 生成或引入新素材时，必须遵守同一套平面投影、比例、光照、阴影和边界规范，不直接拼接具有强透视的独立图片。

未来可以在素材质量和运行时稳定后，增加可选的立体化场景或 2.5D 渲染后端，但升级必须保持以下接口不变：

```text
Character Runtime
Agent State Machine
Behavior Scheduler
Movement Controller
脚底 anchor / visibleBounds 契约
```

立体化升级应通过新版本的场景资产、投影适配器和 Playground 验收完成，不得要求第一版角色重新承担动态透视缩放，也不得破坏现有扁平 2D 角色包。

### 扁平 2D 场景层级提案（已由决策 33 冻结，2026-08-29）

为了在没有真实 3D 深度的前提下表达桌面、椅背和角色的前后关系，PixiJS 场景建议使用固定层级与局部前景遮挡结合的方式：

```text
Background
  → 墙体、地板、固定背景装饰

Back Furniture
  → 桌面后沿、显示器支架、墙边家具后部

Ground Entities (按脚底 y 排序)
  → 漫游角色、工位入口、可站立的场景物体

Front Occluders
  → 桌面前沿、椅背、隔板等需要遮挡角色下半身的部分

Effects / Labels
  → 聊天气泡、状态徽标、点击高亮和调试标记
```

桌子、椅子和其他可能遮挡角色的物体不应被限制为一张完整 PNG，而应允许在 manifest 中声明 `back`、`main`、`front` 三个可选绘制部分。角色以脚底 anchor 参加 Ground Entities 的 y-sort；到达工位后，桌面前沿或椅背的 front 部分再覆盖角色需要隐藏的区域。这样既能保留 Marvis 式的桌面/椅背视觉关系，也不会把角色整张图片错误地压在家具下面。

场景对象同时声明逻辑 `footprint` 和交互命中区域：路径阻挡、目标占用和聊天距离只使用 footprint，点击详情可以使用稍大的 hit area，不能使用角色透明 PNG 的完整矩形作为碰撞边界。PixiJS 只负责按层绘制和排序，不根据纹理内容推断深度。

窗口缩放、角色移动和未来家具加入都不改变层级契约；新增物体只需声明其 anchor、footprint、层标签和可选 front 遮挡部分。该提案仍需结合一张桌子、一个椅子和一个角色在 Playground 中验证后，才能冻结为正式视觉规范。

### 决策 33：扁平 2D 场景使用固定层级和局部前景遮挡

第一版正式采用以下场景绘制顺序：

```text
Background
  → Back Furniture
  → Ground Entities（角色和地面实体，按脚底 y 排序）
  → Front Occluders（桌面前沿、椅背、隔板）
  → Effects / Labels
```

桌子、椅子和可遮挡角色的物体允许拆分为 `back`、`main`、`front` 绘制部分。角色以脚底 anchor 参加 Ground Entities 的排序，工位前沿或椅背的 front 部分负责局部遮挡；不使用纹理内容或真实 3D 深度推断前后关系。

路径阻挡、目标占用和聊天距离使用对象的逻辑 `footprint`，点击详情使用独立的 `hit area`，两者都不使用透明 PNG 的完整矩形。窗口缩放和未来家具扩展只更新坐标与对象元数据，不改变层级契约。

### 决策 34：PixiJS 负责选中，HTML UI 负责详情和控制

角色点击、悬停和场景内高亮由 PixiJS 交互层处理，但详情面板、任务派遣和设置控件继续使用办公室页面中的 HTML UI。两者通过稳定的 `employeeId` 和只读场景快照通信，不通过重建 PixiJS 场景或替换角色节点实现交互。

基本流程：

```text
Pixi pointer event
  → 解析 employeeId
  → 更新 selectedEmployeeId
  → HTML 详情面板读取 Office State

HTML 派遣 / 控制
  → 发送用户指令
  → Runtime Binding / Transition Controller 处理
  → Pixi 场景只消费新的状态快照
```

选中状态只影响高亮、详情面板和可选的路径/目标调试标记，不改变员工的行为优先级、移动速度或动画帧时钟。详情面板关闭、切换员工或窗口缩放时，角色节点必须保持原实例和当前运动进度。

### 决策 35：详情面板采用身份、当前工作、诊断信息三级层级

详情面板的视觉重点按“谁 → 正在做什么 → 运行细节”排列：

```text
员工名称（最大字号）  · 职责短标签（紧邻的小圆点/标签）
当前任务或最近结果（第二视觉焦点，较大字号）
状态、同步、工具、时间、Token、Context、Session（小字号、低对比度）
```

具体规则：

1. 员工名称是面板最醒目的文本，保证用户点击后能立即确认当前查看的是谁。
2. 职责使用名称旁边的小圆点、短标签或颜色标记表达，例如“编码员”“研究员”；职责不是大段说明，也不覆盖真实 Runtime 角色信息。
3. 当前任务优先显示任务标题或摘要；没有进行中的任务时显示最近结果。任务/结果区域字号明显大于诊断字段，但不得伪造不存在的任务内容。
4. `presence`、`runtime`、`sync`、`activity`、最近工具、开始时间、Token、Context 和绑定 Session ID 保留在面板中，但使用较小字号、较淡颜色或折叠区域呈现。
5. 本地漫游、聊天、休息和睡眠明确标记为“办公室活动”，不与真实 Harness 任务混排；睡眠时主区域可以显示“正在休息”，但不能显示为离线。
6. 失败、注意和同步异常需要在诊断区域提供清晰但克制的提示，不能用大面积红色或弹窗打断办公室观察。

面板结构应使用稳定的 HTML 容器，不因字段更新而销毁重建 PixiJS 场景；长任务标题和结果摘要需要截断或换行，保证名称、职责和主信息在窄窗口中仍然可读。

### 角色模块化提案：Character Pack 与 Employee Profile 分层（已由决策 36 冻结，2026-08-29）

为了支持后续更换角色皮肤、增加自定义员工和社区角色，同时避免图片、身份信息与行为逻辑互相污染，角色系统建议拆成两个可独立复用的模板层：

```text
Character Pack
  ├─ 外观与资产
  ├─ 动画序列与能力声明
  ├─ anchor / visibleBounds / footprint
  ├─ 默认人格与行为偏好
  └─ license / author / version

Employee Profile
  ├─ employeeId / displayName
  ├─ role / 职责标签
  ├─ characterId / variant
  ├─ 工作偏好和人格覆盖值
  ├─ 固定工位或席位
  └─ Runtime Binding（由 DshCockpit 维护）
```

Character Pack 只描述“这个角色能怎么显示和默认如何行动”，不保存真实 Session、当前任务或 Token；Employee Profile 只描述“这个员工是谁、承担什么职责和使用哪个角色”，不复制图片和动画。一个角色包可以被多个员工复用，一个员工也可以在不改变 Runtime 身份的情况下更换角色包。

推荐角色包目录：

```text
character-pack/
├── manifest.json          # id、名称、版本、兼容性、许可证、入口
├── assets/
│   ├── atlas/             # Texture Atlas 与 JSON
│   ├── animations/        # walk、working、sleeping 等资源
│   ├── expressions/       # 状态静态图
│   └── preview.png
├── animation/
│   ├── animations.json    # 帧序列、时长、循环和回退声明
│   └── anchors.json       # canvas、visibleBounds、foot anchor
├── personality/
│   ├── profile.json       # traits、mood、偏好
│   └── behavior.json      # 漫游/休息/聊天权重和冷却默认值
├── LICENSE
└── NOTICE
```

角色包不得携带可执行 JavaScript；行为配置只能声明权重、偏好、可用动作和触发条件，实际状态机、移动、Runtime 绑定和 IPC 始终由 Core 提供。Employee Profile 的人格覆盖值也只能在 Core 允许的字段范围内生效，不能修改状态优先级或伪造 Runtime 事实。

模块隔离规则：

1. 角色包解析、素材加载或校验失败时，只禁用该角色包并回退到默认角色，不得使办公室或主程序崩溃。
2. 角色包通过 schema、路径、尺寸、许可证和版本兼容性校验后才能激活；更新采用新版本目录，不覆盖正在使用的资源。
3. 角色包资源、员工身份、Runtime Session 和办公室布局分别持久化，任何一层变化都通过稳定 ID 通知其他层刷新。
4. 新角色作者只需要复制模板、替换 assets、填写 manifest 和 personality 配置，不需要修改 PixiJS、状态机或 Harness 适配代码。
5. 官方、社区和第三方角色继续遵循独立许可证，不因 Core 或 Employee Profile 的许可证发生继承污染。

### 决策 36：角色包与员工资料采用双层模板

第一版正式采用 `Character Pack + Employee Profile` 的双层模板。Character Pack 负责可复用的视觉、动画、锚点、默认人格、行为偏好和许可证；Employee Profile 负责员工名称、职责、角色选择、工位和允许范围内的人格覆盖值。真实 Runtime Session、当前任务和 Token 数据继续由 DshCockpit 的绑定与状态层维护。

两层通过稳定的 `characterId`、`variant` 和 `employeeId` 关联，但不复制对方的数据。角色包不得携带可执行逻辑；员工资料不得修改 Core 的状态优先级、移动规则或 Runtime 事实。角色包加载失败只影响该角色实例并回退到可用角色，员工资料错误只影响该员工配置，不得扩散到其他员工或主程序。

### 决策 37：任务派遣采用空闲直派、忙碌排队和明确抢占

办公室中的任务派遣规则如下：

```text
员工空闲且未绑定任务
  → 直接绑定任务，进入前往工位过渡

员工正在工作或已有任务
  → 新任务进入该员工队列，不自动打断当前任务

用户明确执行抢占或取消
  → 才允许中断当前任务，并记录中断原因

四名常驻员工均忙碌，或任务无法明确归类
  → 使用动态 collaborator 席位
```

排队任务不改变当前员工的 Runtime 事实或工作动画；队列信息在详情面板和活动日志中可见。任务完成、失败、取消或被抢占后，按先进先出顺序处理下一项；如果队列为空，员工解除绑定并恢复本地行为。协作者席位继续遵循同一套排队规则，结束后释放并复用。

### 决策 38：排队任务使用轻量徽标和详情列表表达

排队任务不创建额外角色、不复制化身，也不改变当前执行任务的动画。第一版在四个位置提供一致但克制的队列信息：

```text
角色附近
  → 小型排队数量徽标

详情面板
  → 当前任务 + 等待任务列表

协作者席位
  → 当前任务 + 排队数量

活动日志
  → 记录进入队列、开始执行、完成、取消和抢占
```

徽标只显示数量或简短状态，不覆盖角色主体和脚底锚点；详情面板显示任务标题、入队时间和当前顺序，长文本截断或换行。排队显示属于 UI 状态，不得伪造 Runtime 已经开始执行任务。

### 决策 39：第一版角色包生命周期以本地安全导入为边界

第一版角色包来源限定为内置角色、本地文件夹和本地 ZIP 导入；GitHub 导入、在线市场、远程自动更新和社区发布放到后续阶段。角色包生命周期统一经过：

```text
discovered
  → validated
  → installed
  → active / disabled
  → updated / removed
```

激活前必须校验 manifest schema、稳定 `characterId`、版本兼容性、许可证与作者字段、资源路径越界、图片尺寸、动画能力和 anchor/visibleBounds 数据。角色包不得携带可执行 JavaScript；行为文件只能声明偏好、权重、冷却和动作能力。

每个角色包使用独立目录和版本记录。新版本先在临时位置完成完整校验，再以原子方式切换；正在使用的资源不得被直接覆盖。内置角色不可移除，用户导入的角色可以停用或移除。任一角色包解析、加载或校验失败时，只禁用该包并回退到可用角色，不得影响办公室、其他角色或主程序。

### 决策 40：以 Playground、Character Runtime、Office MVP 三级验收

正式开发按三个相互独立的验收门推进：

```text
Animation Playground
  → Character Runtime
  → Virtual Office MVP
```

**Animation Playground** 使用单角色和纯色背景，验证四方向行走、工作、思考、睡眠、完成、失败、脚底 anchor、帧切换、停止、转向和不同速度下的稳定性。最低通过条件是：方向正确、帧序列连续、左右移动脚底保持同一水平基线、停止和转向不跳帧或瞬移、状态过渡自然、移动速度不改变动画节奏、窗口缩放不改变逻辑锚点和路径、缺少资源时按回退链继续运行。

**Character Runtime** 接入状态机、行为调度、Waypoint Graph、角色包加载和回退机制，验证漫游、聊天、睡眠、任务抢占、任务队列、事件幂等、事件乱序、Runtime 重启和角色包故障隔离。

**Virtual Office MVP** 接入扁平 2D 办公室、六工位、四名常驻员工、一个协作者席位、详情面板和真实 Runtime 事件，验证窗口缩放、暂停恢复、视觉层级、交互、reduced-motion、设置持久化和端到端状态表现。

只有上一层通过验收，才能进入下一层；任何层的失败都应在本层修复，不通过临时 UI 或素材替换掩盖问题。三层测试均需要保留可重复的输入、事件回放和截图/诊断产物。

### 决策 41：协作者席位按先进先出平滑复用

动态 `collaborator` 席位始终只对应一个当前 Runtime Session。当前任务结束、失败、取消或被抢占后，席位先执行离开/清理过渡，并短暂显示“准备中”；随后按先进先出规则绑定下一项排队任务，再执行前往工位和开始工作过渡。

切换期间不创建新的角色实体、不瞬移到新目标点，也不覆盖四名常驻员工的明确绑定。排队数量在协作者席位和详情面板持续可见；队列为空时，协作者回到本地空闲行为或按席位配置暂时隐藏。席位复用只改变 Runtime Binding 和过渡目标，不改变 Character Pack、Employee Profile 或协作者的稳定产品身份。

### 决策 42：本地聊天只显示非文字提示

第一版本地聊天使用侧身相向姿态、聊天动作或轻微待机动作，并显示省略号、交流图标等非文字提示。提示图标作为独立的可替换资源，具体视觉设计后续制作，不把本地模拟聊天伪装成真实 LLM 对话。

只有在未来收到真实 Runtime/Agent 消息事件时，才允许显示消息文本；真实消息与本地聊天提示必须使用不同的数据来源、样式和诊断标记。聊天提示的气泡位置、层级和生命周期由场景 Effects 层管理，不遮挡角色脚底和详情交互区域。

### 决策 43：角色显示尺寸使用 11% 默认值和上下限保护

角色实际可见高度继续以场景可视高度为基准，第一版默认取 `11%`。运行时对最终 CSS 显示高度增加上下限保护：最小 `64px`，最大 `180px`，等价于：

```text
visibleHeight = clamp(64px, sceneHeight * 0.11, 180px)
```

该保护使用 CSS 像素，适用于普通窗口和高 DPI 显示器；它只限制最终显示尺寸，不改变逻辑场景坐标、移动速度、脚底 anchor 或图片内部的 source-pixel manifest。所有状态图、行走帧和协作者实例共享同一尺寸计算规则。

### 决策 44：素材校准输出独立 validation-report.json

每个角色包的素材预处理生成独立的 `validation-report.json`，用于验收、诊断和素材版本追踪，不作为 Character Runtime 的业务输入。报告至少记录角色包 ID、源文件列表、统一画布、阈值、逐帧检测值、人工覆盖值、最终 anchor、visibleBounds、误差、警告、失败原因和总体结果。

推荐结构：

```json
{
  "characterId": "whale-girl",
  "canvas": { "width": 2508, "height": 2508 },
  "thresholdPx": 1,
  "frames": [
    {
      "src": "walk-left-01.png",
      "detectedAnchor": { "x": 1254, "y": 2349 },
      "overrideAnchor": null,
      "finalAnchor": { "x": 1254, "y": 2350 },
      "delta": { "x": 0, "y": 1 },
      "visibleBounds": {},
      "status": "passed"
    }
  ],
  "result": "passed",
  "warnings": []
}
```

报告文件可以随角色包版本保存，但不应由运行时动态修改。运行时只读取经过校验的 manifest 和最终资源；如果报告缺失或结果不是 `passed`，角色包应在激活阶段重新校验或被拒绝。

### 决策 45：持久化配置和事实，不持久化瞬时动画过程

办公室持久化分为配置/历史事实与瞬时运行过程两类。以下内容应持久化：当前角色选择、Employee Profile、睡眠阈值、动画/行为设置、最近任务与活动日志，以及 Runtime Binding 的可恢复快照。以下内容不持久化：当前漫游路径、当前动画帧、聊天锁、临时目标占用和过期的移动过渡。

窗口关闭或重新打开时，恢复员工配置、设置和历史记录；本地行为从安全初始点重新选择目标，不重放关闭期间的移动时间。Runtime 重启后重新执行事件同步和绑定校验，不直接恢复旧的 `running`、`completed` 或 `failed` 状态；只有收到当前 `sessionEpoch` 的可信事件后，才恢复对应 Runtime 表现。持久化失败只能降级为默认配置并写入诊断日志，不得阻塞办公室启动。

## 历史未决问题（已由后续决策取代）

早期讨论曾把以下项目列为未决；它们现在分别由决策 26、29、32–45 和本节规格审查修订冻结。保留本段仅用于追溯，不应作为实现输入：

- 员工聊天的具体动作、朝向、停留时长和是否显示气泡。
- 角色显示比例、最小/最大 CSS 尺寸、工位比例和层级关系。
- DeepSeek 娘的角色动作帧与素材校准格式。
- 办公室本地状态持久化范围与 Runtime 重启后的绑定恢复策略。

真正仍开放的内容只包括素材制作本身（例如补帧和家具图），不改变 Runtime、状态机或资源契约。

## 规格审查修订（2026-08-30）

对五份 Character Runtime 规格进行交叉审查后，补充并冻结以下实现前契约：

1. **Runtime 事件适配**：办公室侧统一使用 `eventId/sessionId/sessionEpoch/sequence/eventType/payload` 信封。当前 Harness 直接提供 `seq`，不提供全局事件 ID 或运行代际；因此由 State Adapter 生成带来源标记的 `eventId/sessionEpoch`，并用规范化 payload 指纹做短窗口去重。序号前跳最多缓存 64 条或 2 秒并请求 resync；超时丢弃缓存并标记 `sync=stale`，不猜测中间状态。
2. **同步与本地行为**：`sync=stale/resyncing` 本身不结束漫游、聊天、休息或任务表现。只有新的可信 Runtime 事实或明确用户指令可以抢占。同步状态只更新徽标、诊断和恢复流程。
3. **用户控制边界**：用户可以中断办公室移动/动画，并对已验证的 Session 请求 cancel/interrupt；preempt 只作为 Office 队列策略。当前 Harness 未提供 pause/resume，第一版 UI 不暴露这两个控制。任何控制都不能伪造 Runtime 结果；取消进入 `cancellationPending`，直到 Harness 确认终止前保留绑定。
4. **完成/失败时序**：终端事件先锁存 `lastResult` 并让旧绑定进入 releasing；结果动画默认最多 5 秒。FIFO 队列在结果展示结束后启动，显式紧急派遣可以抢占结果展示；完成和失败均继续队列。队列为空时才释放到本地行为。`runtime` 的终端事实和操作性的 binding 生命周期可以短暂并存。
5. **移动与资源契约**：移动速度按 `min(sceneWidth, sceneHeight)` 的比例换算，四舍五入不会改变逻辑位置；Waypoint Graph 使用版本化 JSON、显式有向/无向边、容量和带过期时间的 reservation。`manifest.json` 只提供 metadata 入口，anchors/animations 文件分别作为唯一几何和动画数据源；v1 atlas 禁止 trim/rotate。
6. **可验证性与持久化**：Playground 默认使用 fixture graph，点击吸附到可达 waypoint；帧时长、脚底基线、移动速度、resize 误差和到达误差均有自动阈值，视觉自然度另行人工复核。持久化只保存配置、历史和带 `sessionEpoch` 的可恢复绑定快照，不保存路径、帧、聊天锁或瞬时过渡；旧代际快照不能恢复运行态。

这些修订已同步到 `docs/superpowers/specs/2026-08-30-character-*.md` 与 `animation-playground-plan.md`。若本记录与旧段落冲突，以本节和对应正式规格为准。

## 设计纪律

- **文档先行**：任何实现前，先完成产品行为、模块边界、数据契约、错误/降级语义和验收标准；聊天中的口头结论必须同步到版本化文档。
- **先规格、后计划、再代码**：当前阶段只补齐研究和规格；用户确认规格后才写 implementation plan；用户确认 plan 后才拆分开发 spec 和实现任务。
- **接口先冻结**：跨进程、跨模块或跨版本的接口先写 schema、来源、版本和兼容策略；没有证据的 Runtime 能力必须标为 adapter 派生或未支持。
- **阶段门禁**：Playground、Character Runtime、Office MVP 各自拥有独立的测试/视觉验收门；前一阶段未通过，不进入后一阶段。
- **责任层修复**：素材问题在素材校准层修复，事件问题在 State Adapter 修复，路径问题在 Movement 修复；不得用临时 CSS、UI 文案或状态覆盖掩盖底层错误。
- **范围纪律**：implementation plan 必须列出文件、接口、测试、回滚边界和明确不做项；发现与总纲冲突时暂停并记录，不擅自扩大范围。
- 不把工具名称、provider 名称或任务 label 误当成永久业务角色。
- 不伪造 Runtime 工作、Token、错误或完成状态；办公室本地模拟行为不能产生 LLM 调用和 Token 消耗。

## 当前最大不确定性与遗漏清单（实现前登记，2026-08-30）

本节不是新的产品决策，而是实现前的风险登记。已完成源码研究的项目不再以“假设”描述；仍需真实素材、Electron 接线或目标运行时探针验证的项目继续保留。

### 研究已完成、接线仍需验证：真实 Harness 事件能力

官方源码已经证明：Session 事件是 `type/seq/time/data`，Agent 状态是 `idle/running`，存在 `agent/status`、`Agent.cancel`、`followup/steer/inject/whenIdle`、`subagent/start/end`、descriptor、`session.control/follow/page`。官方源码没有证明 `eventId`、`sessionEpoch`、Office snapshot/resync、通用 pause/resume/preempt。对应处理和字段来源已写入 `docs/research/HARNESS-RUNTIME-EVIDENCE-2026-08.md` 与状态机规格。实现前仍需用目标 Harness 版本做一次脱敏兼容探针，确认当前 RPC 接线和版本差异；探针结果必须回写证据报告。

### 最高风险：素材是否真的构成可用 Walk Cycle

脚底 anchor 校准只能解决几何漂移，不能补足 Contact、Passing、重心和步幅缺失。如果现有四方向图片不是同一角色、同一画布和同一动作周期生成的，代码无法把它们变成自然行走。必须在 Playground 中对真实 DeepSeek 娘素材做逐帧检查，并允许“补帧或重制素材”成为验收结论，而不是强行进入 Runtime。

### 高风险：PixiJS 与现有 Electron 壳的生命周期接缝

当前分支没有 PixiJS 依赖，旧办公室实现已归档。`office.html`、WebContentsView 创建/销毁、preload、CSP、本地资源 URL、窗口隐藏/恢复和高 DPI 行为需要一份实际接线设计；否则 Character Runtime 即使单元测试通过，也可能在 Electron 中出现空白、纹理泄漏或重复 ticker。

### 高风险：投影、家具遮挡和实际布局

扁平 2D 方向已经确定，但六工位的最终比例、角色显示高度、桌面/椅背的 back/front 拆分、通道宽度和聊天点仍未用真实素材冻结。没有一套最小可运行的桌子、椅子、角色 fixture，无法验证“角色重点不被家具遮挡”以及放大角色后是否拥堵。

### 高风险：用户控制与 Runtime 能力的边界

控制边界已经完成源码审查并冻结：`cancel` 映射 `Agent.cancel`/`subagent.interrupt`；`preempt` 只是 Office 的“cancel 当前 + 等待终止 + 再派发”队列策略；当前未发现原生 pause/resume，因此第一版 UI 隐藏或置灰，不伪造 paused Runtime 状态。`followup`、`steer`、`inject` 保持各自语义，不能冒充恢复。控制超时、RPC 不可用或终止原因未知时只显示 pending/diagnostic，保留 binding，不渲染完成、失败或离线。完整矩阵见证据报告和 `2026-08-30-character-state-machine.md`。未来若目标 Runtime 增加明确能力，必须通过版本化 adapter capability 再开放。

### 容易遗漏的产品问题

1. **隐私和信息暴露**：任务摘要、工具参数、错误信息和 Token/Context 数据是否允许直接出现在办公室场景或截图中；是否需要脱敏、截断和“隐私模式”。
2. **启动与加载体验**：角色包加载、纹理解码、首次失败、升级迁移和缺失素材时，用户看到什么占位状态，多久后显示诊断，是否允许先显示场景再渐进加载角色。
3. **可访问性**：reduced-motion 之外，还需要键盘选中、焦点顺序、屏幕阅读器可读的详情面板、颜色对比度和不依赖动画才能理解状态的文本。
4. **时间与恢复语义**：系统休眠、电脑时间跳变、窗口后台、应用崩溃重启、Runtime 重连时，5 分钟睡眠计时、5 秒结果展示和本地行为种子如何保持可解释。
5. **状态历史与诊断**：事件被丢弃、resync 超时、fallback、队列等待和控制超时需要怎样展示、保留多久、如何导出，才能支持复现“角色为什么没动”。
6. **多窗口/单实例约束**：多个办公室视图是否允许同时打开，谁拥有唯一模拟时钟，关闭一个窗口是否影响其他窗口，主进程与 renderer 如何避免重复绑定。
7. **角色包安全边界**：除路径越界和 JavaScript 禁止外，还需要限制 ZIP 炸弹、超大图片、解码耗时、符号链接和恶意 metadata，避免导入角色包拖垮应用。
8. **版本和兼容性**：PixiJS、Electron、角色包 schema、Office State schema 和 Harness Runtime 协议分别如何版本化，哪些升级可以热切换，哪些必须禁用并提示用户。
9. **视觉回归基准**：需要固定参考窗口尺寸、DPI、字体、截图时刻和允许差异；否则“看起来更自然”无法在后续素材或代码更新中自动比较。
10. **产品降级策略**：没有角色包、没有 GPU、WebGL 初始化失败、Runtime 长时间不可达、窗口性能不足时，办公室是显示静态模式、诊断模式，还是允许用户关闭动画但保留详情和日志。
